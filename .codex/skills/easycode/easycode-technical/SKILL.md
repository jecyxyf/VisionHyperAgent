# EasyCode 技术方案

## 职责与输入

- 只负责目标项目的 `specs/REQ-002-技术方案设计.md`。技术方案以用户明确确认的 `specs/REQ-001-产品需求文档.md` 为基线，讨论技术约束、选型、架构、模块与组件、依赖方向及接口概览。
- 技术方案只概述接口类别、名称与作用；详细签名和契约留待后续文档工作。此技能不生成项目目录、模块 API、代码规范、AGENTS.md 或开发计划，不实现业务代码。
- 只讨论或维护本技能时，不为当前仓库自动生成项目技术方案；不自动安装工具、编译、部署、提交或推送。

## 入口与续做

1. 确定目标项目根目录，读取有效项目规则及产品需求文档，并核对用户对整份产品需求的明确确认。需求缺失、尚未确认或与本次目标冲突时，指出具体问题，先交回产品需求阶段，不把技术方案写在未经确认的需求之上。
2. 先检查 `specs/REQ-002-技术方案设计.md` 是否存在。已有文档时阅读全文，结合本次要求和可核实的确认记录，只讨论未完成或受变更影响的部分，保留其他已确认内容；文件存在不等于整份技术方案已确认。
3. 没有文档时，读取主技能中的[技术方案模板](../easycode/templates/技术方案模板.md)，调用已可用的 `brainstorming` 技能，按模板章节逐一讨论。一次只问一个关键问题；每章结束复述关键决定与取舍并请用户确认，不套用模板中的示例架构或技术栈。
4. 中断后重新读取现有文档及能核实的用户确认，从尚未完成的相关章节继续。确认依据缺失时只核对受影响的决定，不重访无关章节或猜测答案。

## 创建初版

1. 模块设计达到首次成文门槛即可创建初版，不必等整份方案所有细节都齐全。门槛是模块及所属架构层、职责与边界、依赖方向、公开接口的类别及作用已明确；确实没有依赖或公开接口的模块，按用户确认的事实说明，不虚构内容。
2. 写入前提供目标路径、已有依据、拟写章节、未决内容及核对方式的完整计划，取得用户同意，再创建 `specs/REQ-002-技术方案设计.md`。已确定的结论据实写入；尚未讨论清楚的部分明确标为待确认，不填模板占位值，不把初版称作最终方案。
3. 初版交用户审阅。产品需求中的目标、验收与技术方案中的约束、模块职责、依赖和接口概览应能对应；发现冲突或缺口时指出，不擅自改写已确认的产品需求。

## 审阅与完成

1. 用户提出修改时，先读取当前正文并定位受影响章节；写入前给出完整修改计划并取得同意，再局部修订。若修改改变产品行为或验收，先交回产品需求阶段确认，不把技术方案的决定冒充产品需求。
2. 核对架构层、模块、组件归属、职责边界、调用方向、接口概览与运行流程的一致性；待确认项和未执行的检查如实说明，不用未经验证的断言补齐文档。
3. 只有用户明确确认整份技术方案后，才交付其路径与确认范围供后续普通任务按获批计划生成其他文档、目录或开展开发；本技能不自动继续执行这些任务。
