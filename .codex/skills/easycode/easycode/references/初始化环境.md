# 项目初始化

本说明只在执行目标项目的 EasyCode 流程或恢复初始化时读取。检查本身是只读的；工具安装、hooks、2119 配置和 Git 忽略规则都是目标项目的写入操作，必须先说明完整计划并取得同意。只维护技能时不在当前仓库运行安装脚本。

## 1. 核对目标环境

1. 确定目标项目根目录及生效的项目规则。检查 brainstorming 是否已在当前环境被发现且可用，并核对实际 `SKILL.md` 和必要资源；已有可用技能不下载、不升级、不覆盖。
2. 缺少 brainstorming 时，先核对用户提供或本机可访问的完整技能来源及安装位置。来源不明时询问；仅在用户明确批准来源、目标路径和可能的联网行为后，才按当前可用的 `skill-installer` 说明安装。若需新会话才能发现技能，说明情况并暂停，不把文件存在当作已加载。
3. 检查目标项目本地的 `.codex/tools/rfc2119/`、安装材料、实际 CLI 版本、`.2119.yml` 和 `.codex/hooks.json`；分别记录已安装、已配置、待授权及已验证的证据，不能只靠目录或文件存在判断就绪。

## 2. 安装或修复 2119

1. 已有可用安装时不重复安装。缺失时先核对目标项目实际可用的离线安装包或其他用户确认的来源；本技能不附带 2119 程序或压缩包，也不默认联网安装或复制另一项目的已安装 `node_modules`。
2. 若采用 `init-environment.mjs` 离线材料，核对完整脚本、`offline/` 清单及压缩包。当前这套脚本使用 rfc2119 0.7.0、picomatch 4.0.7 和 yaml 2.9.1，要求 Node.js >=20、npm >=9；材料或运行时不全时请用户提供或确认处理方式，不自行改用在线 npm/npx。
3. 执行前逐项列出目标项目中的 `.codex/tools/rfc2119/`、`.2119.yml`、`.codex/hooks.json`、`.gitignore` 及实际会改变的内容；核对已有文件，保留其他配置。已有 `specs/` 却没有 `.2119.yml` 时，先确认正式需求扫描范围，不能静默排除旧文档。缺少完整材料、出现路径冲突或未获批准时停下。
4. 若用户批准且脚本及离线包已部署在目标项目的 `.codex/tools/rfc2119/`，才从目标项目根目录执行，并将技能路径替换为实际 brainstorming 目录：

```text
node .codex/tools/rfc2119/init-environment.mjs --project . --brainstorming "<实际技能目录>"
```

脚本会合并本地 hooks，并可能创建或更新上述配置与安装文件。不得把这个命令用于脚本不在目标项目的位置；换安装方法时重新核对版本、来源、写入范围和验证方式。

## 3. 配置与验证

1. 检查本地 CLI 与锁定版本及安装结果；核对 `.2119.yml` 覆盖实际正式需求文档，并包含 `specs/models/**/*.md` 中的模块 API；不能缩小既有扫描范围来让检查通过。产品需求、技术方案和开发进度不因文件名带 `REQ` 就自动当成 2119 规范。
2. 核对 `SessionStart`、`PostToolUse`、`Stop` 的 hooks 都指向项目本地 CLI；可运行性手工测试与宿主真实触发分开记录。宿主要求项目信任或 hook 审批时交用户在宿主中完成，不修改全局信任或伪造批准。
3. 通过新会话和实际事件核对需要的 hook 激活情况；无法观察的事件标记“待验证”，不得把配置存在、脚本输出或手工调用说成真实触发。无法完成必要授权或激活时暂停初始化，保留现场供下次恢复。
4. 初始化后可用本地 CLI 核对配置，示例为 `node .codex/tools/rfc2119/node_modules/rfc2119/dist/cli.js check`。零要求的通过只说明检查可执行，不代表模块测试或评审通过。后续 API 文档有要求时，按真实测试和评审结果说明未完成部分。

初始化结果只报告环境证据与阻碍，不写入开发计划；真正开发任务的进度在规划完成后另记。
