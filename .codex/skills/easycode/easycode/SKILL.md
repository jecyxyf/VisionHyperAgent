# EasyCode 主技能

## 入口与范围

- 确定目标项目根目录，读取有效项目规则、已有文档及实际状态。所有产出路径相对于目标项目；仅讨论或维护 EasyCode 技能时，不在当前仓库执行项目初始化或生成业务项目文档。
- 本技能依次负责初始化环境、衔接产品需求、衔接技术方案、检查并完成五类后续文档及其已获批的目录和配置。产品与技术方案分别由 [easycode-product](../easycode-product/SKILL.md) 和 [easycode-technical](../easycode-technical/SKILL.md) 负责；不替子技能确认整份文档。
- 写入、安装或改动环境前，先给出涉及路径、来源、步骤及核对方式的完整计划，取得用户明确同意。未经要求不创建业务代码、运行编译部署或执行 Git 提交和推送。
- 中断后重新检查环境、文档正文、可核实的确认记录和工作区，只续做未完成或受变更影响的步骤。文件存在、初版已写入或用户没有反对，都不代表整份文档已经确认。

## 固定执行步骤

1. **项目初始化。**读取[初始化说明](references/初始化环境.md)，检查 brainstorming 是否可用、项目本地 2119 是否可执行，以及 hooks 是否已配置、获得必要授权并在宿主真实触发。缺失时按确认的来源和获批计划安装、修复；安装成功或手工运行通过不等于 hooks 已激活。初始化有阻碍时说明并停下，恢复后再继续。
2. **产品需求。**检查 `specs/REQ-001-产品需求文档.md` 和明确确认记录。未完成或受变更影响时进入[产品需求子技能](../easycode-product/SKILL.md)，由用户审阅初版、提出修改；整份需求确认后进入下一步。
3. **技术方案。**以已确认的产品需求为依据，检查 `specs/REQ-002-技术方案设计.md` 和明确确认记录。未完成或受变更影响时进入[技术方案子技能](../easycode-technical/SKILL.md)，由用户审阅初版、提出修改；整份方案确认后才进入生成步骤。
4. **自动化检查与生成。**先核对目标项目中已有文档、模块归属、相关目录和 2119 配置，再列出本轮要创建或修订的文件、实际目录、依据、顺序与验证方式，获用户同意后按下面的次序处理。已有内容只修订受影响部分，模板示例不当作项目事实：
   - 用[项目结构模板](templates/项目结构模板.md)检查或形成 `specs/REQ-003-项目结构.md`。依据技术方案先列实际及规划的模块和目录；后续 API、计划和规范落定后回查并更新结构表，只创建本轮获批且确实需要的目录。
   - 用[模块（组件）API 模板](templates/模块（组件）API模板.md)逐个检查或形成 `specs/models/` 下的文档，明确真实公开契约，核对 `.2119.yml` 包含这些文档。签名或行为不清楚时向用户确认；要求与测试的 2119 编号如实对应，不造接口、测试或通过结果。
   - 用[开发计划及进度模板](templates/开发计划及进度模板.md)检查或形成 `specs/plans/开发计划及进度.md`，列明阶段边界、任务依赖、对应 API/2119 要求、真实进度与验收方法。尚未编码和运行的测试记为待完成；阶段划分不清楚时先由用户确认。
   - 用[代码规范模板](templates/代码规范模板.md)检查或形成 `specs/REQ-004-代码规范.md`，依据实际语言、项目规则及有效的 Google 或语言官方规范；再核对开发计划中的检查命令与规范是否一致。
   - 最后用[AGENTS 模板](templates/AGENTS模板.md)检查或合并项目根目录 `AGENTS.md`，保留已有规则、替换真实技能路径，核对所有保留的文档入口和阶段停顿规则。

## 完成与退出

- 检查产品目标、技术模块、项目结构、API、计划、规范和 AGENTS 的对应关系；必要的配置和目录按事实标记，未执行的测试、2119 评审及未通过的检查明确留给开发计划，不冒充已经验收。
- 缺少批准、工具来源、整份文档确认或关键接口决定时，停在受影响步骤，说明阻碍；之后从该步骤恢复，不强行宣布整个技能完成。需求或方案改变时先回到最早受影响的子技能，再局部同步下游文档。
- 五类文档及获批的相关内容检查完成后，交用户人工审查并结束 EasyCode 技能。后续文档优化和按开发计划逐阶段编码是另行启动的工作；即使 goal 仍在进行，也不自动进入编码。
