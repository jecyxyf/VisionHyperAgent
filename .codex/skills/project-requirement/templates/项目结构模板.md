## 二、补充说明

- `specs/` 保存契约，`src/` 保存业务源码及 `depends/` 下的外部依赖，`tests/` 保存对应验证；层、模块和组件名称均以已确认的技术方案和 API 文档为准。技术栈要求其他源码或测试布局时，保持归属关系并按真实路径填写，不为了匹配示例重排现有工程。
- 根目录 `bin/` 是编译结果的固定输出目录，便于调试和发布。项目实际构建配置应指向该目录；模板只说明目标位置，不表示已修改构建脚本或已经编译出产物。
- 模块 API 文档为 `specs/models/<架构层名称>/REQ-NNN-<模块名>.md`；有独立公开契约的组件文档放在 `specs/models/<架构层名称>/<模块名>/components/REQ-NNN-<组件名>.md`。组件不提升为同级模块，模块与组件各用独立编号；未拆组件的模块不创建同名文档目录。
- `specs/requirements/` 仅在确有独立 2119 规范时使用。模块与组件的开发和测试要求写在各自 API 文档末章；开发计划引用要求 ID，不复制契约。检查 `.2119.yml` 只扫描真实的正式规范和 API 文档，叙述性的产品、架构及进度文档不因此冒充 2119 规范。
- `specs/plans/开发计划及进度.md` 仅用于开发任务拆解和执行进展，不记录环境安装、需求设计确认或变更审批。没有实际开发规划任务时，不创建计划文件或空 `plans/` 目录。
- `.codex/skills/` 只有技能确实安装在项目内时才列出；离线 2119 位于 `.codex/tools/rfc2119/`，不放进技能目录。不要添加不存在的工具、资源目录或源码文件。
- 项目结构文档区分“已存在”与“规划”；代码规范和 AGENTS.md 在后续阶段生成后更新状态，不因模板出现路径就创建空目录、空文件或对话记录。
