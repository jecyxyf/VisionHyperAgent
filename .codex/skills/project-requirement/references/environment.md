# 初始化环境

只在执行目标项目规划、恢复流程或修复第一阶段环境时读取。本说明不授权创建业务源码、修改全局信任设置或启动整套业务规划；仅维护技能时不生成目标项目的规划文档。

## 1. 确认项目与 brainstorming

- 确定目标项目根目录、当前技能实际路径和现有项目规则。续做时先读进度；可用的已有技能与工具不下载、不升级、不覆盖。
- 从当前环境公布的技能清单和实际目录找到 brainstorming，读取 `SKILL.md`，检查名称及其所需本地资源。不能把“文件存在”当成宿主已发现或本次已加载。
- 缺失时优先请用户提供本地完整技能目录或离线包，保留配套资源，遵循实际技能安装目录规则。已有目录损坏时先报告差异，不覆盖用户内容；需要重新启动会话才能发现新技能时说明并暂停。
- 没有可用本地来源时，暂停并询问来源。仅在用户明确授权初次联网获取后，读取当前环境的 skill-installer 说明，使用确认的来源安装单个 brainstorming 技能；不安装整套插件或反复重试代理。下载失败或超时即报告阻塞，后续重试或更换来源须另行确认。

## 2. 安装固定版本的离线 2119

本技能只提供安装说明，不携带 2119 源码、安装脚本或离线包。实际工具统一部署在目标项目 `.codex/tools/rfc2119/`；当前项目的绝对路径为 `/home/xyf/workspace/VisionHyperAgent/.codex/tools/rfc2119`。

运行前检查 **Node ≥20、npm ≥9**；缺失时请用户提供可用本地运行时，不自行联网安装。工具目录内的 `offline/` 保存清单、锁文件及三个原始 npm tgz：

| 包 | 固定版本 |
| --- | --- |
| rfc2119 | 0.7.0 |
| picomatch | 4.0.7 |
| yaml | 2.9.1 |

新环境必须单独取得工具部署材料，将 `init-environment.mjs` 与完整 `offline/` 放入目标项目的 `.codex/tools/rfc2119/`。复制技能不包含这些材料；缺失时请求用户提供，不复制到技能目录，也不回退联网获取。

在目标项目根目录执行，替换 brainstorming 的实际路径：

```bash
node .codex/tools/rfc2119/init-environment.mjs --project . --brainstorming "<实际技能目录>"
```

脚本检查 brainstorming，校验离线材料，以本地缓存和严格离线模式安装到目标项目 `.codex/tools/rfc2119/`，并创建或合并本地 hooks。材料、运行时或依赖不完整时按报错修复，不执行在线 npm/npx，不以 `--prefer-offline` 代替严格离线安装。

运行副本会应用离线补丁：取消原版 SessionStart 的更新探测，将 CLI 提示改为本地 Node 命令；原始 tgz 与许可证保留。后续检查、review 和记录 verdict 都使用本地 CLI；在目标项目根执行，例如：

```bash
node .codex/tools/rfc2119/node_modules/rfc2119/dist/cli.js check
```

保留现有项目的需求、评审结果和其他 hook 配置。安装或手工测试成功只证明对应步骤完成，脚本不能代替宿主审批，也不能证明 hooks 已真实激活。

### 正式需求的扫描范围

- 对全新、没有 `.2119.yml` 且 `specs/` 下没有既有文档的项目，默认只扫描 `specs/requirements/**/*.md`。后续需要门禁的正式需求按 RFC 2119 格式写入该目录，并为强制要求补充真实测试与独立评审。
- 本技能生成的产品、架构、API、进度等叙述性规划文档不是自动合格的 RFC 规范；文件名带有 `REQ-` 也不代表符合格式。它们保留原定输出位置，不因初始化而伪装为正式需求。
- 已有 `.2119.yml` 时保留其扫描范围；已有 `specs/` 文档但没有配置时，脚本拒绝自动选范围，先请用户确认哪些文档属于正式需求并配置。不得静默排除既有需求、改窄扫描范围或删除旧规范来让门禁变绿。
- 初始化不生成假需求、占位测试或通过判决。**零要求的 `check: PASS` 只说明工具配置可运行，不代表需求已被测试或验收完成**；初始化完成也不豁免后续正式需求的测试和评审。

## 3. 配置与激活 hooks

依次区分以下证据，不能只检查 `.codex/hooks.json` 是否存在：

1. **安装**：本地 CLI 及三包版本符合锁文件，更新探测已经取消；缺材料或损坏时没有在线回退。
2. **配置**：目标项目的 `SessionStart`、`PostToolUse`、`Stop` 分别调用本地 CLI 的 `hook session-start`、`hook after-edit`、`hook stop`，并指定 `--platform codex`；保留无关 hooks。
3. **手工测试**：分别验证三个 hook 的本地调用及返回内容。此项只能证明命令可执行，不等同于宿主加载了配置或触发了事件。
4. **宿主授权**：用 `codex features list` 核对 hooks 支持与启用状态；已启用则不重复修改。项目需要信任或 hook 文件需要审批时，让用户在宿主中明确信任目标项目，并通过 `/hooks` 审查、批准当前具体 hook 定义；不能自动写入全局 trust、修改审批记录或计算信任 hash 代替用户授权。宿主显示已发现、已启用、已信任仍不等于事件已触发。
5. **真实激活**：新建或重开会话验证 SessionStart，并通过无业务影响的实际工具编辑和正常会话结束确认 PostToolUse 与 Stop 的实际触发。记录宿主提供的 `hook/started`、`hook/completed` 或等效证据中的事件、来源路径及结果；不能观察时写“待验证”，不把脚本的手工 smoke 输出当成真实事件。新会话用于验证启动事件及新技能加载，不表示每次审批都必须重启。

宿主版本不支持相应功能、审批未完成或新会话无法验证时，记录具体阻塞并暂停第一阶段；不编造未知 flag，也不为通过检查而绕过审批。配置变更后重新核对宿主是否要求再次审批。

## 4. 记录与完成条件

按进度模板分别记录实际路径、版本、安装结果、配置结果、手工测试、用户授权、真实激活证据及剩余阻塞，并处理脚本报告中 `requiredNextSteps` 指明的待办。全部必需项都就绪，才将“初始化环境”标为已完成并继续产品需求；脚本退出成功不自动满足此条件。

对恢复任务保留原记录与用户内容，核对失效项后局部更新。不要因本次修改技能或仅修复环境而自动生成一套产品、架构、API 等业务规划文档。
