# 项目需求与全局规划

## 目标与边界

- 首次规划按“初始化环境 → 产品需求 → 技术方案设计 → 模块 API → 项目结构 → 代码规范 → AGENTS 文档路由”执行，不把项目结构提前到模块 API 之前。续做和局部修订先核对环境与相关正式文档，再按下面的流程恢复、变更回退规则进入必要阶段，不无故重写整套文档。
- 用户只在讨论或修改本技能时，只处理技能及其配套资源，不为当前仓库自动生成一套项目方案。
- 除第一阶段必需的本地工具与 hooks 配置外，本技能只交付设计与规则文档，以及用户明确要求的开发计划与进度；文档中的 API 示例不代表业务实现已经完成。未经另行要求，不创建业务源码、不编译部署、不提交或推送。
- 模板只约束章节、图表和表达方式。ImageBatch、MVVM、C++、Qt 等都是示例，不是目标项目的默认架构或技术选型。
- 开始前确定目标项目根目录，读取其有效项目规则和已有文档。所有产出路径相对于目标项目，不能误写到技能安装目录。
- 复杂对象允许采用“驱动对象模块（model）+依赖组件（components）”的组织方式；驱动对象拥有整体职责，组件归属于该驱动对象，不自动提升为同级模块。

## 对象模块与组件归属

1. 当技术方案确认某个对象属于驱动层且对象内部存在多个相对独立的依赖对象时，建立一个驱动对象模块作为归属根，再在该模块目录下建立 `components/`。
2. 源码目录采用以下结构表达归属关系；`modelA` 是驱动对象模块，`componentX` 是它的从属组件：

```text
modelA/
├── modelA 源代码
└── components/
    └── componentX 源代码
```

3. 一个驱动对象模块可以包含多个组件。组件只能通过所属模块的公开契约参与上层调用；除非技术方案明确将组件提升为独立模块，否则不得把组件并列到架构模块清单。
4. 文档必须与代码保持同样的归属关系：驱动对象模块文档说明自身功能、组件清单及必要的依赖方向；每个组件只生成一个对象文档，不再拆成多个对象文档。模块与组件各自使用模块（组件）API 模板，组件也要说明自身功能及实际存在的接口，不能只写与父模块的差异；共享契约引用唯一归属，不重复父模块契约。
5. 模块 API 路径使用 `specs/models/<架构层名称>/REQ-NNN-<模块名>.md`；当组件需要独立记录公开对象契约时，组件对象文档使用 `specs/models/<架构层名称>/<model>/components/REQ-NNN-<component>.md`，并由 model 文档列出和链接。模块与组件各分配一个全项目唯一的稳定 `REQ-NNN`；组件文档必须放在所属驱动对象的文档归属范围内，并在文档中明确“所属模块、组件名称、上层调用入口和依赖组件”；不能创建无归属的组件文档或重复契约。
6. 组件内部可以有私有辅助类型或实现文件，但它们不生成独立的公开对象文档；只有被技术方案提升为公开模块的对象，才重新进入模块清单和 API 设计流程。

## 设计流程恢复

1. 识别本次是首次规划、继续未完成设计，还是局部修订；只维护本技能时，不生成目标项目的正式文档或开发计划。
2. 续做时读取本次相关的正式需求、技术方案、API、结构、代码规范和 AGENTS.md，结合当前对话中可核实的用户确认，继续最早尚未完成的相关工作；已确认且不受影响的章节不重新采访。
3. 文件存在或自动检查通过不等于用户确认。若找不到明确的确认依据，或正文与本次变更不一致，只核对受影响的结论，不把无关模块的待办当作整套流程的阻塞，也不以开发计划代替设计确认。
4. 从开发或接口接入进入时，以相关正式文档和实际变更判断契约是否仍有效；已有开发计划可用于查任务与进度，但不能替代产品、架构、API 或 2119 要求。纯查询和只读审查可继续，并注明所读版本的状态。

## 变更回退与联动更新

发现新需求或既有设计需要改变时，明确变更点、最早受影响阶段和待同步的正式文档，再按下表处理。未受影响的阶段不重做；开发计划只在其任务安排受影响时更新，不作为设计确认记录。

| 变更影响 | 最早回到的阶段 | 确认与同步范围 |
| --- | --- | --- |
| 产品目标、功能、交互、业务规则或验收 | 产品需求 | 先确认产品变更，再检查相关架构章节、模块 API、结构、规范与路由 |
| 技术栈、架构层、模块职责或依赖 | 技术方案设计 | 逐章确认受影响设计，先更新技术方案，再更新相关 API 和其后受影响的文档 |
| 模块内部的公开接口、消息、委托或数据类型，不改变产品和架构 | 模块 API | 明确尚未决定的契约，更新该模块及调用方文档；发现上游影响则继续回退 |
| 文件位置、目录规划或文档路径，不改变模块职责 | 项目结构 | 更新目录映射及各文档中的相关路径，不重新讨论未变化的产品和接口 |
| 语言风格、注释或检查工具 | 代码规范 | 自动更新规则及已有 API 示例的对应表达，不擅自重命名已确认的公开接口 |
| 路由分类或链接错误 | AGENTS 文档路由 | 修正路由和必要索引；若暴露缺失的设计，返回对应阶段处理 |
| 驱动对象、组件归属或对象拆分方式 | 技术方案设计 | 先确认 model / component 边界，再同步项目结构、模块 API 和代码规范中的目录及文档说明 |

1. 新决定尚未确认时，保留原已确认正文，指出受影响文档及待确认事项；不得把旧确认自动转移到新决定上，也不把受影响文档作为最新已确认依据继续推进。
2. 用户直接、明确指定的决定可作为该决定的确认，不重复问相同问题；它不等于确认整份文档。产品和架构中仍未决定的部分继续通过 brainstorming 确认，代码规范的常规选择仍自动完成。
3. 确认后先局部回写最早受影响的正式文档，再按依赖顺序同步相关 API、结构、规范和路由；不是直接跳回原阶段继续生成，也不是覆盖全部旧文档。保留无关的用户手工内容。
4. 架构层或模块更名时先明确旧名到新名的映射，同步 API 文件位置、目录表、相互引用及路由。确认废弃的文档再迁移或删除，不能留下两个互相矛盾的有效版本。
5. 完成后双向核对：架构里的模块都有 API，API 也都有架构归属，调用双方契约一致，引用指向最新位置。未同步的产物明确指出，不能提前宣布完成；若现有开发计划受影响，再更新其相关任务。

## 1. 初始化环境

1. 确定目标项目根目录，读取[环境初始化说明](references/environment.md)。核对现有技能、Node/npm、本地离线材料和 hooks；2119 安装与项目 hooks 写入目标项目，不误写技能目录。
2. 检查并加载现有 brainstorming，已经可用则不下载、不升级、不覆盖。缺失时优先使用用户提供的本地完整技能包；没有来源则暂停询问，仅在用户明确授权后才使用 skill-installer 初次下载，不默认联网重试。
3. 按环境说明将 `rfc2119@0.7.0` 离线安装到目标项目 `.codex/tools/rfc2119/`，取消更新探测，以本地 Node CLI 执行。本技能仅交代安装流程，不包含 2119 源码、安装脚本或离线包；部署材料缺失时请求提供，不能复制回技能目录或回退在线 npm/npx。
4. 创建或合并本地 `SessionStart`、`PostToolUse`、`Stop` hooks，保留其他配置。按环境说明分别验证手工调用和宿主真实激活；需要用户完成的功能启用、项目信任或 hook 审批明确交还用户，不伪造授权。
5. 核对并如实汇报路径、版本、安装／配置／激活证据及阻塞，不写入开发计划。只有 brainstorming 已可用、离线 2119 安装通过且 hooks 真实激活已验证，才视为环境就绪并进入产品需求；仅文件存在、脚本成功或手工 hook 成功均不够。

使用 brainstorming 的采访、方案比较和确认能力，但本任务的交付范围与输出位置按本技能执行；不因通用工作流自行转入业务编码、创建额外实施计划或自动提交。

## 2. 产品需求：只讨论产品

1. 调用 brainstorming，以采访方式了解目标用户、问题、使用场景、功能、交互、业务规则、优先级、范围及验收标准。每次聚焦一个关键问题，根据回答追问，不一次抛出长问卷。
2. 不在此阶段讨论或写入编程语言、框架、分层、源码目录、数据结构、接口、数据库方案等实现选择。用户提到实现偏好时留待架构阶段处理，不能污染产品需求文档。
3. 用户可感知的使用环境、支持的文件类型、体验目标及隐私要求可以记录，但不附带技术实现方式。
4. 按模板生成 `specs/REQ-001-产品需求文档.md` 草案，复述关键需求并检查完整性。尚未决定的问题明确标识，不自行补成已确认需求。
5. 等待用户明确确认产品需求后，根据确认范围修订正式文档，再进入技术方案设计；不能把文档存在、用户未反对或草案已写入视为确认。修订已确认产品需求时先按变更回退规则处理，不将设计确认写入开发计划。

## 3. 技术方案设计：按章节确认

1. 读取已确认的产品需求和技术方案模板，按章节调用 brainstorming，与用户逐章讨论设计。
2. 章节结构和图表形式参考模板；技术栈、架构层、模块、第三方依赖及数据流必须来自目标项目需求，而不是复制 Demo。
3. 当前章节先说明关键决策与取舍，得到用户确认后再将结论写入该技术方案章节并推进下一章；未确认的部分明确标为草案。恢复时只重访受变更影响的章节。确实不需要的能力说明“不适用”及理由，不为套模板增加插件或其他功能。
4. 将确认内容整理到 `specs/REQ-002-技术方案设计.md`。可逐章保存草案用于继续讨论，但不得把尚未确认的章节标为最终方案。
5. 统一架构层名称、模块名称、职责和依赖关系；根据实际文档和用户逐章确认的结论检查完成条件，所有章节确认且相互一致后，进入模块 API 阶段。局部修订只处理受影响的确认与同步。

## 4. 模块 API：依据架构细化模块与组件

1. 从已确认的产品需求和技术方案提取相关功能、模块与组件清单、所属架构层、职责、依赖及接口清单，按依赖顺序细化 API。技术方案只概述有哪些接口，API 文档逐项承接并定义详细契约，不借细化擅自新增接口或改变职责。
2. 模块与组件分别使用同一份模块（组件）API 模板：第 1 章“功能”和第 6 章“模块调用实例”必填；第 2—5 章依次为“数据结构”“属性”“方法”“消息回调”，只保留实际存在的公开接口，没有对应内容则整章省略，不为填表发明接口。组件写自身能力及接口，并注明所属模块；必要的归属、调用方向和依赖在功能介绍中简述，不另写详细设计章节。
3. 方法与消息回调逐项说明功能、实际签名、输入参数和输出参数／返回值；数据结构写字段及类型，属性写类型与访问方式。必要的约束、错误反馈、异步最终结果等在相关接口下简要说明，不增加通用行为、生命周期或错误处理固定表格。只有关键方法按需附加简要实现原理，不能把每个 API 条目写成私有实现说明。
4. 已明确的内容直接整理；遇到影响用户行为、模块职责、公共协议或架构边界的缺口，执行“变更回退与联动更新”：先确认并回写受影响的上游文档，再继续 API 设计，不只采访后就跳过上游更新。
5. 签名与调用实例使用目标技术方案确定的语言；第 6 章各为模块或组件提供一个简短的自身公开接口调用场景，说明输入、调用和预期结果。组件实例从所属模块的调用方向出发，不伪造上层对组件的直接入口；必要的接口局部示例仍可放在对应条目中。所有手写代码遵守本技能的注释规则，不要求用完整 Demo 串起全部方法或声称未实现的代码已可运行。
6. 将模块文档保存到 `specs/models/<架构层名称>/REQ-NNN-<模块名>.md`；组件文档保留在所属模块的 `components/` 下并使用各自的 `REQ-NNN-<组件名>.md`。编号选择尚未被现有文档占用的全项目唯一编号，标题 `# REQ-NNN: ...` 与文件名一致，发布后不因插入或删除其他要求而重编已有编号。层名来自已确认架构，不按仓库或包另行分组，不创建 `<模块名>/<模块名>.md`。路径段不得为空或包含目录分隔符、路径穿越片段。
7. 如果模块采用 model + components 结构，模块文档简要列出组件归属、调用方向和组件清单；组件文档按“对象模块与组件归属”规则保存，每个组件使用同一模板写明自身功能及适用的接口，不能只写接口表、父模块契约副本或差异，也不按方法、数据结构或子对象继续拆分文档。
8. 双向核对技术方案接口清单与 API 详情，不遗漏、不擅自新增；技术方案中的同步响应归入方法输出，消息触发的回调归入消息回调，其他公开回调按实际调用关系归入方法条目，不强行称为消息回调。检查跨模块与组件的类型、签名、参数、输出和必要约定是否一致；共享类型确定唯一归属，其他对象引用定义。
9. 每份 API 文档先用固定 `## Overview` 标题提供 2119 所需概览，最后用固定 `## Requirements` 标题编写“开发与测试要求”；其下分别用 `### REQ-NNN.1: 开发要求` 和 `### REQ-NNN.2: 测试要求` 作为分类标题。两类下的条目按 `1.`、`2.` 等顺序排列，工具自动生成 `REQ-NNN.1.1`、`REQ-NNN.2.1` 等完整 ID；每条仅写一个可独立验证的 RFC 2119 约束，不把分类标题当成一条要求，也不在正文手写另一套 ID。测试要求写真实场景和预期结果，不以“必须有测试”取代可测试的行为。按实际接口写足必要条目，未明确的关键约束先确认，不编造占位要求。
10. 确认目标项目 `.2119.yml` 的扫描范围包含 `specs/models/**/*.md`，保留已有正式需求文件的扫描范围；如果修改扫描范围会影响既有文档，先核对和处理，不静默排除要求或以缩小扫描范围使门禁变绿。每个强制要求都要有标注完整 ID 的真实测试及独立的新上下文质量评审；运行本地测试及 `2119 check`，零要求的通过不算接口已验收。
11. 每个模块或组件文档写完后核对所属层与模块、实际路径、契约及未完成检查；中断后从尚未完成的相关文档继续，不重生成无关模块，也不把设计生成过程记入开发计划。

## 5. 项目结构：最后整理目录与职责

1. 模块 API 完成后，再读取项目结构模板，结合架构、模块文档与仓库现状生成 `specs/REQ-003-项目结构.md`。
2. 将目录、文件、类型与简要说明合并在同一张表格中，保留末尾同级“补充说明”章节，不另拆文件说明表。
3. 准确列出正式文档以及 `specs/models/<架构层名称>/REQ-NNN-<模块名>.md`。实际项目涉及的源码、测试、资源、构建等位置按已确认规划补充，不套用 Demo 目录。
4. 区分已存在与规划项；代码规范和 AGENTS.md 在这一阶段可以标记“后续生成”。只编写结构说明，不因表中列出路径就创建空目录、源码或对话记录。
5. `specs/plans/` 只在实际需要时存放开发计划及进度等开发任务文档；`开发计划及进度.md` 不承载环境检查、需求设计确认或变更审批。本阶段不自动创建计划文件。
6. 对采用 model + components 的模块，在同一张目录表中同时列出驱动对象目录、`components/` 目录和组件文件，并在“简要说明”中写明“组件归属于哪个驱动对象”；不得只列组件文件而省略所属模块。
7. 在 `src/depends/` 规划外部依赖的位置，在项目根目录 `bin/` 固定存放编译结果以便调试和发布；区分已有与规划，未实际配置的构建输出不得声称已落到 `bin/`，也不因模板列出路径就创建目录。

## 6. 代码规范：自动生成

1. 依据已确认的技术栈、模块接口与目录职责识别目标语言；已有源码和构建清单用于核对。不能把模板 Demo、第三方依赖或生成代码的语言当成项目语言。
2. 查阅对应的 Google 官方语言规范，入口为 `https://google.github.io/styleguide/`。Google 未提供该语言规范时，使用语言官方规范并明确标注，不能杜撰“Google 某语言规范”。记录采用的标题、来源地址与实际查阅日期。
3. 根据实际语言直接制定命名、格式、注释、模块边界、错误处理、日志、并发、资源管理、测试与审查规则，生成 `specs/REQ-004-代码规范.md`；不再为普通风格选择逐章采访用户。
4. 若无法在线核验来源，明确标注未核验范围并沿用可验证的现有项目规则，不伪造查询结果。格式化与检查命令须区分已配置和建议配置，不声称未执行的检查已通过。
5. 以下注释规则属于用户指定的项目要求，对所有手写程序语言生效，优先于参考规范中的风格建议：
   - 每连续 5 行非空源码中至少有 1 行有效功能注释；空行不能稀释频率，最多连续 4 行没有注释的代码。
   - 注释简短直接，只描述对应代码的功能。不得用开发过程、修复历史、无关背景、空注释或装饰线凑数量。
   - 独立注释或同行注释均可，但必须使用对应语言的合法语法。字符串里的注释符号不是注释；禁止为满足频率而改动字符串数据或破坏代码语义。
   - 纯数据文件、第三方文件和机器生成文件不当作手写源码插入注释；不支持注释的数据格式不能写入非法注释。不能借此豁免某一种程序语言。
6. 用代码规范模板明确计数口径和检查方法；本次 API 若包含代码示例，回查并同步符合语言规则和注释要求，不重写已确认的接口，也不为本阶段检查另行添加示例。
7. 检查完成后核对已有相关示例，简短汇报本次更新结果，不把开发计划误用成额外的设计确认关卡。

## 7. AGENTS：只生成文档路由

1. 前述文档完成后读取 AGENTS 模板与项目已有 AGENTS.md，输出项目根目录的 `AGENTS.md`，不放在 specs/。
2. 仅保留任务类型到文档的映射，以及按需读取、跨任务组合、缺失处理和冲突处理规则；不复制产品需求、技术方案设计、API 细节或编码规范正文。
3. 将模板中的 `{{需求技能路径}}` 替换为本技能实际可访问路径，优先使用项目内相对路径。模块任务按架构层和模块名读取对应 API，不把占位路径或通配符当成真实链接。
4. 保留已有编译、打包、部署等本次未替代的有效路由；相同任务合并必读文档，避免生成重复或矛盾入口。不预设尚不存在的编译规范文档。
5. 校验所有路由目标存在且可读，规范大小写与相对路径；保留现有文档中的用户内容，不用整份模板直接覆盖有效的自定义路由。
6. 同步更新项目结构文档，把已经实际生成的代码规范和 AGENTS.md 从规划项改为已生成；其他规划项仍按事实标注。
7. 区分“查阅或按既定方案实现”与“设计、改变既定方案”：需求、架构、API、目录规划及代码规范的设计修订都必须路由回本技能及相关正式文档；普通代码规范修订仍自动完成，纯查阅不启动访谈。继续未完成设计时查受影响的正式文档，不把开发计划当作设计流程进度。
8. 编码和接口接入路由必须明确读取相关 API、技术方案和代码规范；已有开发计划时另读对应任务及实际进度，不能以任务状态代替有效接口契约。相关正式文档待确认、待更新或相互冲突时，先按变更回退规则核对，不能直接按旧契约实施；纯查询和只读审查可注明版本状态后继续。
