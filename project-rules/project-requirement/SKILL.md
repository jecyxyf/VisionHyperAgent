# 项目需求与全局规划

## 目标与边界

- 首次规划按“准备 → 产品需求 → 技术方案设计 → 模块 API → 项目结构 → 代码规范 → AGENTS 文档路由”执行，不把项目结构提前到模块 API 之前。续做和局部修订按下面的进度恢复、变更回退规则进入必要阶段，不无故重写整套文档。
- 用户只在讨论或修改本技能时，只处理技能及模板，不为当前仓库自动生成一套项目方案。
- 本技能只交付设计与规则文档；API 调用 Demo 属于文档示例，不代表业务实现已经完成。未经另行要求，不创建业务源码、不编译部署、不提交或推送。
- 模板只约束章节、图表和表达方式。ImageBatch、MVVM、C++、Qt 等都是示例，不是目标项目的默认架构或技术选型。
- 开始前确定目标项目根目录，读取其有效项目规则和已有文档。所有产出路径相对于目标项目，不能误写到技能安装目录。

## 模板与产出

模板路径相对于本 SKILL.md；只在进入对应阶段时读取，不一次性加载全部模板。

| 阶段 | 技能内模板 | 产出 | 推进方式 |
| --- | --- | --- | --- |
| 准备 | [进度记录模板](templates/进度记录模板.md) | 可用的 brainstorming；`specs/plans/REQ-005-需求设计进度.md` | 检查依赖后初始化或恢复进度 |
| 产品需求 | [产品需求模板](templates/产品需求模板.md) | `specs/REQ-001-产品需求文档.md` | 采访，生成草案，等待用户确认 |
| 技术方案设计 | [技术方案模板](templates/技术方案模板.md) | `specs/REQ-002-技术方案设计.md` | brainstorming 逐章讨论、逐章确认 |
| 模块 API | [模块API模板](templates/模块API模板.md) | `specs/models/<架构层名称>/<模块名>.md` | 逐模块设计，关键缺口继续采访 |
| 项目结构 | [项目结构模板](templates/项目结构模板.md) | `specs/REQ-003-项目结构.md` | 模块 API 完成后汇总 |

| 文档路由 | [AGENTS模板](templates/AGENTS模板.md) | 项目根目录 `AGENTS.md` | 根据有效文档自动生成或合并 |

## 进度记录与恢复

1. 先识别本次是首次规划、继续未完成流程，还是局部修订，确定用户实际要求的范围。只维护本技能时，不创建目标项目的进度文件。
2. 项目规划时先读取 `specs/plans/REQ-005-需求设计进度.md` 及相关成果。没有进度文件时，在完成准备检查后按进度模板初始化；它只记录本流程状态，不是业务开发实施计划，不增加第八个阶段。
3. 记录当前阶段、已完成产物、架构章节完整标题、已确认结论、用户确认依据、待处理问题及下一步。用户确认、产物检查完成、出现阻塞或阶段切换时立即更新，不等整套文档结束才记录。
4. “已确认”必须有用户明确确认依据，不能由文件存在、沉默或自动检查推出；API、结构、规范和路由可按阶段规则记录“已完成”，不额外要求逐份人工确认。确认依据只保存简短的决定摘要，不保存完整聊天、密钥或私有配置。
5. 恢复时对照实际文档、确认范围和现有变更，继续最早尚未完成的相关事项；已确认且未受影响的章节不重新采访。正文与记录不一致或无法判断是否仍符合确认结论时，标记待核对，仅就差异定向询问。
6. 已有成果但没有进度记录时，不用模板覆盖原文。用户明确指定的已确认基线可以记录沿用；其他状态写“未核对”，不能擅自写“已确认”。只在本次任务需要该确认而证据不足时询问，不把局部规范修订变成整套产品访谈。
7. 进度记录是索引，不替代正式需求、架构或 API 契约。只更新本次涉及的记录，保留用户已确认结论和其他模块的有效内容；局部修订只汇报本次完成范围，不因此宣称整个流程完成。
8. 从编码或接口接入任务进入时，先读取相关模块、本次依赖契约和关联变更的进度，再选择有效 API。即使单项标为已完成，只要关联变更未同步或记录与正文不一致，仍须先核对。缺少记录时只核实当前相关基线，不凭文件存在放行，也不把无关模块的待办当成整个项目的阻塞；纯查询和只读审查可继续并注明版本状态。

## 变更回退与联动更新

发现新需求或既有设计需要改变时，先在进度记录中列出变更点、最早受影响阶段和待同步文档，再按下表处理。未受影响的阶段不重做。

| 变更影响 | 最早回到的阶段 | 确认与同步范围 |
| --- | --- | --- |
| 产品目标、功能、交互、业务规则或验收 | 产品需求 | 先确认产品变更，再检查相关架构章节、模块 API、结构、规范与路由 |
| 技术栈、架构层、模块职责或依赖 | 技术方案设计 | 逐章确认受影响设计，先更新技术方案，再更新相关 API 和其后受影响的文档 |
| 模块内部的公开接口、消息、委托或数据类型，不改变产品和架构 | 模块 API | 明确尚未决定的契约，更新该模块及调用方文档；发现上游影响则继续回退 |
| 文件位置、目录规划或文档路径，不改变模块职责 | 项目结构 | 更新目录映射及各文档中的相关路径，不重新讨论未变化的产品和接口 |
| 语言风格、注释或检查工具 | 代码规范 | 自动更新规则及 API Demo 的对应表达，不擅自重命名已确认的公开接口 |
| 路由分类或链接错误 | AGENTS 文档路由 | 修正路由和必要索引；若暴露缺失的设计，返回对应阶段处理 |

1. 新决定尚未确认时，保留原已确认正文，在进度记录中保存变更提议，并将受影响产物标为“待更新”；不得把旧确认自动转移到新决定上，也不把受影响文档作为最新已确认依据继续推进。
2. 用户直接、明确指定的决定可记录为该决定的确认，不重复问相同问题；它不等于确认整份文档。产品和架构中仍未决定的部分继续通过 brainstorming 确认，代码规范的常规选择仍自动完成。
3. 确认后先局部回写最早受影响的正式文档，再按依赖顺序同步相关 API、结构、规范和路由；不是直接跳回原阶段继续生成，也不是覆盖全部旧文档。保留无关的用户手工内容。
4. 架构层或模块更名时先明确旧名到新名的映射，同步 API 文件位置、目录表、相互引用及路由。确认废弃的文档再迁移或删除，不能留下两个互相矛盾的有效版本。
5. 完成后双向核对：架构里的模块都有 API，API 也都有架构归属，调用双方契约一致，引用指向最新位置。逐项更新进度，未同步的产物仍保持“待更新”，不能提前宣布完成。

## 1. 准备：检查并加载 brainstorming

1. 优先检查当前环境公布的技能清单与实际路径，读取名为 brainstorming 的 SKILL.md。现有且可用时直接使用，不下载、不升级、不覆盖。
2. 缺失时按用户已确认的流程下载安装。默认来源为 `obra/superpowers` 仓库的 `skills/brainstorming`；用户明确指定来源时使用其来源并核对内容。
3. 优先使用当前环境的 skill-installer，读取其说明并定位实际安装脚本。命令形式如下，按环境选择 python3 或 python，先替换脚本路径，不原样执行占位符：

```bash
python3 "<skill-installer目录>/scripts/install-skill-from-github.py" --repo obra/superpowers --path skills/brainstorming --ref main
```

4. 遵循安装器的目标目录规则（通常为 `$CODEX_HOME/skills`，未设置时为 `~/.codex/skills`）。没有安装器时，将同一来源下载到系统临时目录，只复制该技能及其配套资源到实际技能安装目录；不安装整套插件、不修改无关全局配置。
5. 安装后检查 SKILL.md 的 name、说明及所需本地资源，再加载技能。若目标已存在但损坏，不静默覆盖用户内容；如果环境要求下一轮才识别新技能，明确提示并暂停，不能冒充已加载。
6. 安装器最多调用两次，每次设置总超时（建议 60 秒）。遇到下载不完整、压缩包损坏或下载中断时，仅清理本次临时下载，可对同一来源、同一 ref 使用安装器的 `--method git` 备用一次。禁用交互式凭据提示，不切换到不明来源，不覆盖已有技能；仍失败、超时或遇到无权访问时说明原因并暂停，不跳过准备阶段或反复下载。
7. 技能可用后按“进度记录与恢复”初始化或恢复项目规划记录，准备阶段标为已完成。已有记录只核对更新，不重新套用模板覆盖。

使用 brainstorming 的采访、方案比较和确认能力，但本任务的交付范围与输出位置按本技能执行；不因通用工作流自行转入业务编码、创建额外实施计划或自动提交。

## 2. 产品需求：只讨论产品

1. 调用 brainstorming，以采访方式了解目标用户、问题、使用场景、功能、交互、业务规则、优先级、范围及验收标准。每次聚焦一个关键问题，根据回答追问，不一次抛出长问卷。
2. 不在此阶段讨论或写入编程语言、框架、分层、源码目录、数据结构、接口、数据库方案等实现选择。用户提到实现偏好时留待架构阶段处理，不能污染产品需求文档。
3. 用户可感知的使用环境、支持的文件类型、体验目标及隐私要求可以记录，但不附带技术实现方式。
4. 按模板生成 `specs/REQ-001-产品需求文档.md` 草案，复述关键需求并检查完整性。尚未决定的问题明确标识，不自行补成已确认需求。
5. 等待用户明确确认产品需求后，同步记录确认范围、结论及下一步，再进入技术方案设计；不能把文档存在、用户未反对或草案已写入视为确认。修订已确认产品需求时先按变更回退规则处理。

## 3. 技术方案设计：按章节确认

1. 读取已确认的产品需求和技术方案模板，按章节调用 brainstorming，与用户逐章讨论设计。
2. 章节结构和图表形式参考模板；技术栈、架构层、模块、第三方依赖及数据流必须来自目标项目需求，而不是复制 Demo。
3. 当前章节先说明关键决策与取舍，得到用户确认后立即按完整章节标题记录确认结论、依据与遗留问题，再推进下一章。恢复时只重访受变更影响的章节。确实不需要的能力说明“不适用”及理由，不为套模板增加插件或其他功能。
4. 将确认内容整理到 `specs/REQ-002-技术方案设计.md`。可逐章保存草案用于继续讨论，但不得把尚未确认的章节标为最终方案。
5. 统一架构层名称、模块名称、职责和依赖关系；根据实际文档及逐章确认记录检查完成条件，所有章节确认且相互一致后，进入模块 API 阶段。局部修订只处理受影响的确认与同步。

## 4. 模块 API：依据架构逐模块生成

1. 从架构文档提取模块清单、所属架构层、职责与依赖，按依赖顺序逐模块细化 API。
2. 使用模块 API 模板，填写公开数据结构、属性、方法、消息与事件、委托与回调、错误处理、生命周期、线程安全及依赖。没有的能力写“不适用”，不强行发明接口。
3. 已明确的内容直接整理；遇到影响用户行为、模块职责、公共协议或架构边界的缺口，执行“变更回退与联动更新”：先确认并回写受影响的上游文档，再继续 API 设计，不只采访后就跳过上游更新。
4. 每份文档将调用示例独立放在最后，用一个完整 Demo 串起该模块全部公开方法；方法章节只写接口契约，不重复堆放调用片段。用目标语言表达，并遵守本技能约定的注释规则。
5. 保存到 `specs/models/<架构层名称>/<模块名>.md`。层名来自已确认架构，不按仓库或包另行分组，不再创建 `<模块名>/<模块名>.md`。路径段不得为空或包含目录分隔符、路径穿越片段。
6. 逐项复核模块清单是否都有文档，跨模块类型、方法签名、消息和错误约定是否一致。共享类型确定唯一归属，其他模块引用定义，不各写一份不同版本。
7. 每个模块文档写完并检查后，记录所属层、实际路径、完成状态与未完成检查；中断后从尚未完成的相关模块继续，不重生成无关模块。

## 5. 项目结构：最后整理目录与职责

1. 模块 API 完成后，再读取项目结构模板，结合架构、模块文档与仓库现状生成 `specs/REQ-003-项目结构.md`。
2. 将目录、文件、类型与简要说明合并在同一张表格中，保留末尾同级“补充说明”章节，不另拆文件说明表。
3. 准确列出正式文档以及 `specs/models/<架构层名称>/<模块名>.md`。实际项目涉及的源码、测试、资源、构建等位置按已确认规划补充，不套用 Demo 目录。
4. 区分已存在与规划项；代码规范和 AGENTS.md 在这一阶段可以标记“后续生成”。只编写结构说明，不因表中列出路径就创建空目录、源码或对话记录。
5. `specs/plans/` 存放临时开发计划及本技能的 `需求设计进度.md`。进度记录用于续接流程；业务开发计划仍只在实际需要时另行编写，不因此新增自动生成开发计划的阶段。

## 6. 代码规范：自动生成

1. 依据已确认的技术栈、模块接口与目录职责识别目标语言；已有源码和构建清单用于核对。不能把模板 Demo、第三方依赖或生成代码的语言当成项目语言。
2. 查阅对应的 Google 官方语言规范，入口为 `https://google.github.io/styleguide/`。Google 未提供该语言规范时，使用语言官方规范并明确标注，不能杜撰“Google 某语言规范”。记录采用的标题、来源地址与实际查阅日期。
3. 根据实际语言直接制定命名、格式、注释、模块边界、错误处理、日志、并发、资源管理、测试与审查规则，生成 `specs/REQ-004-代码规范.md`；不再为普通风格选择逐章采访用户。
4. 若无法在线核验来源，明确标注未核验范围并沿用可验证的现有项目规则，不伪造查询结果。格式化与检查命令须区分已配置和建议配置，不声称未执行的检查已通过。
5. 以下注释规则属于用户指定的项目要求，对所有手写程序语言生效，优先于参考规范中的风格建议：
   - 每连续 5 行非空源码中至少有 1 行有效功能注释；空行不能稀释频率，最多连续 4 行没有注释的代码。
   - 注释简短直接，只描述对应代码的功能。不得用开发过程、修复历史、无关背景、空注释或装饰线凑数量。
   - 独立注释或同行注释均可，但必须使用对应语言的合法语法。字符串里的注释符号不是注释；禁止为满足频率而改动字符串数据或破坏代码语义。
   - 纯数据文件、第三方文件和机器生成文件不当作手写源码插入注释；不支持注释的数据格式不能写入非法注释。不能借此豁免某一种程序语言。
6. 用代码规范模板明确计数口径和检查方法；回查本次 API 调用 Demo，同步符合语言规则和注释要求，不重写已确认的接口。
7. 检查完成后直接记录本阶段及相关 Demo 的更新结果，不把进度记录误用成额外的用户确认关卡。

## 7. AGENTS：只生成文档路由

1. 前述文档完成后读取 AGENTS 模板与项目已有 AGENTS.md，输出项目根目录的 `AGENTS.md`，不放在 specs/。
2. 仅保留任务类型到文档的映射，以及按需读取、跨任务组合、缺失处理和冲突处理规则；不复制产品需求、技术方案设计、API 细节或编码规范正文。
3. 将模板中的 `{{需求技能路径}}` 替换为本技能实际可访问路径，优先使用项目内相对路径。模块任务按架构层和模块名读取对应 API，不把占位路径或通配符当成真实链接。
4. 保留已有编译、打包、部署等本次未替代的有效路由；相同任务合并必读文档，避免生成重复或矛盾入口。不预设尚不存在的编译规范文档。
5. 校验所有路由目标存在且可读，规范大小写与相对路径；保留现有文档中的用户内容，不用整份模板直接覆盖有效的自定义路由。
