本文确定软件框架、职责与目录分层，不提前细化未确认的业务模块或接口。当前已实现工程骨架、Slint 宿主、日志／配置底层，以及按功能划分的 MainWindowViewModel、ConfigViewModel；设置页参数编辑和模型业务尚未接入。

## 1. 总体选择：先保持简单

- 采用模块化单体，以一个 Rust + Slint 主程序承载软件交互和业务控制。
- 首版不拆分前端、后端两个主可执行程序，不建立前后端 ZeroMQ 通信或内部 ZeroMQ 总线。
- Codex CLI 和 Python Worker 可以作为软件管理的内部执行进程，不作为需要用户分别部署的后端产品。
- ZeroMQ 保留为对外图片识别接口；相机输入继续采用 OpenCV。
- 保持方案 A：私有 Python/PyTorch 环境训练 YOLO26，Rust 执行生产推理。

六层表示职责，不要求每次调用逐层经过，也不要求每层独立成为进程、crate 或顶层目录。

## 2. 六层职责

| 层级 | 核心职责 | 边界 |
| --- | --- | --- |
| 1. 用户交互层（View） | 呈现 ViewModel 的状态，接收用户输入并转为 ViewModel 命令，负责界面绑定。 | 业务交互只面向 ViewModel，不直接访问 Foundation、Driver、Agent 或应用服务。 |
| 2. 运行核心层（ViewModel） | 按功能划分，每个 ViewModel 负责对应界面的交互、状态和流程，调用 Foundation、Driver 或共享能力。 | 不依赖 UI 类型、窗口对象或 UI 事件循环；没有 View 也可运行与测试。不把业务放入 View，也不由 MainWindowViewModel 包办所有模块。 |
| 3. Agent 层 | 管理 Codex 交互、Skills、任务规划和工具调用，执行由运行核心协调的智能工作流。 | 通过统一能力接口执行任务，不另写一套业务实现，不拥有 Python 环境管理职责。 |
| 4. 应用层 | 封装可复用的业务能力、校验和数据操作，由 ViewModel 组织调用。 | 不绑定 UI，不建立与运行核心相互脱节的另一套控制状态，也不让界面或 Agent 文本决定业务事实。 |
| 5. 驱动／适配层 | 封装外部技术和执行程序的具体操作，接收请求并返回执行结果或状态通知。 | Python Worker、YOLO、Rust 推理、OpenCV、ZeroMQ 的调用适配归于此层；不直接操作 View 或改写 ViewModel 内部状态。 |
| 6. 基础层 | 提供日志、配置、路径、通用资源及进程支撑，管理私有 runtime 的定位与校验。 | 不承载模型排名、训练策略或标注规则等业务决策。 |

表中的技术名称用于说明归属，不是已经确定的业务模块清单。各层具体模块、类、接口和模块内文件将在后续逐层设计。

### 2.1 MVVM 的项目约定

**按功能划分的 ViewModel 层是实际运行核心；每个 View 连接对应的 ViewModel，而不是所有功能都交给 MainWindowViewModel。**

```text
用户 ↔ View ↔ ViewModel → Foundation / Driver
                   └─→ 可复用的 Agent / 应用能力
```

箭头表示调用与职责方向，结果经明确接口或状态通知返回。View 不直接调用底层；ViewModel 不持有具体 View，也不依赖 Slint 数据类型或事件循环。绑定及 UI 线程切换属于 View 适配职责。Agent 工具经抽象能力接口或消息提交请求，由运行核心处理，不形成 Agent 与具体 ViewModel 对象的双向依赖。

- `MainWindow ↔ MainWindowViewModel`：主窗口交互、导航、子模块协调，不代理配置 CRUD。
- `配置界面 ↔ ConfigViewModel → ConfigManager`：配置初始化、加载、读取、修改和保存。ConfigViewModel 已实现，现有 SettingsPage 的参数编辑尚未绑定。
- 主窗口 ViewModel 可持有并初始化子 ViewModel，但不代替子模块执行其交互逻辑；其他功能按后续授权补充对应 ViewModel。

悬停、焦点、动画与纯布局状态可保留在 View，但实际任务执行和运行状态不能依赖这些 UI 对象。按钮与对话复用同一运行核心及业务实现；没有 UI 时，同一个 ViewModel 仍须能够初始化并执行核心流程。该要求不表示已增加无界面产品模式或独立后端程序。

### 2.2 桌面装配与基础服务初始化

当前启动顺序为：

```text
main → view::run
  → 创建 MainWindow
  → 创建 MainWindowViewModel 及子 ConfigViewModel（构造不执行 I/O）
  → MainWindowViewModel::run 建立 foundation::with_logging 作用域
    → ConfigViewModel::init → CONFIG.init
    → View 绑定主窗口导航 → Slint 事件循环
  → Foundation 自动完成日志收尾 → main 返回退出码
```

View 只处理窗口创建、接口绑定及 UI 事件循环；主窗口 ViewModel 协调共享日志生命周期和子模块初始化，配置操作由 ConfigViewModel 自己负责。损坏配置恢复返回安全提示，由主窗口协调记录 WARNING；初始化失败不继续运行任务。创建窗口失败时先保留错误，在日志可用后记录并返回失败。

非 UI 调用方可以独立使用 ConfigViewModel，也可在 MainWindowViewModel::run 中执行不涉及窗口的任务。日志写入、配置读写和安全收尾仍由 Foundation 实现，不增加对外 `flush` 或 `shutdown`。设置页编辑、训练等业务仍待接入，不将这次职责拆分描述为完整业务 MVVM 已交付。

## 3. Python 相关职责归属

| 内容 | 归属 |
| --- | --- |
| Python 解释器、依赖环境的定位、版本与完整性管理 | 基础层 |
| Python Worker、YOLO 训练/评估/导出调用及执行结果处理 | 驱动／适配层 |
| 训练任务的运行流程、运行状态与执行协调 | ViewModel |
| 可复用的训练业务校验与数据操作 | 应用层，由 ViewModel 组织调用 |
| 训练策略、调参决策及工具调用 | Agent 层 |

这不是把 Python 物理拆成多套环境。软件仍管理一套与发行版匹配的私有训练环境，使用者不需要自行配置 Conda 或系统 Python。

Agent 使用 Python 支撑的业务能力，不因此拥有解释器、依赖安装或运行环境生命周期的管理职责。

## 4. 按钮与对话共享业务能力

软件的业务功能需要同时支持界面操作和对话操作。ViewModel 提供统一运行入口，并复用应用服务或底层适配能力；两个入口使用相同的校验、执行和状态变化，不复制业务实现。

### 4.1 普通操作

- 按钮入口：View → ViewModel → Foundation／Driver；需要共享业务封装时，由 ViewModel 调用应用服务。
- 对话入口：View → ViewModel → Agent 工作流 → 工具接口 → 同一运行核心的能力接口。

普通操作不必先经过大模型。例如，按钮和对话都可以触发同一相机控制能力，但按钮无需为了完成该操作先调用 Agent。

### 4.2 智能操作

- 自动标注、自动调参等智能按钮通过 ViewModel 启动相应 Agent 工作流。
- 对话入口由 Agent 理解任务后进入同一工作流。
- Agent 通过工具接口使用运行核心的统一能力，复用相同应用服务与适配实现，不为按钮再实现一套独立的智能编排。

### 4.3 Skills 与工具的关系

- Skills 指导软件功能的使用方式、任务规则和工作流程。
- 工具接口把 Agent 的调用映射到运行核心提供的能力，不复制业务实现。
- 软件功能需要有对应的 Agent 调用能力和技能指引，但不要求每个按钮都建立一个独立 Skill。
- 强制业务规则在运行核心调用的统一业务路径中校验，可由应用服务封装；例如，Agent 工具不能绕过训练前的用户标注确认。

具体能力清单、工具名称、输入输出和 Skill 组织方式，留待各层模块设计时确定。工具接入协议尚未选定，不在本框架中锁定具体实现。

## 5. 关键业务流程

### 标注与人工确认

用户通过 View 提交图片与要求 → ViewModel 组织 Agent 初标 → ViewModel 调用共享能力登记结果 → View 呈现 → 用户修改并确认 → ViewModel 校验并更新可供训练使用的状态。

不额外引入独立辅助标注模型。初标质量和可编辑区域的表达方式仍按 PRD 的未决事项后续验证，不因确认架构就宣称已经解决。

### 自动训练与模型产出

用户通过 View 确认并发起训练 → ViewModel 组织 Agent 制定候选参数 → ViewModel 创建并协调任务 → 驱动层调用 Python Worker → 执行器返回指标与产物 → ViewModel 更新运行状态并调用共享能力登记结果 → Agent 决定继续调参或选择模型 → 完成部署产物导出与验证。

Agent 负责策略，ViewModel 负责运行流程和状态，应用服务可封装共用校验与数据操作，执行器负责实际计算。不能仅凭 Agent 的“训练完成”回复判定成功。指标、预算和停止条件仍需后续确认，不在框架中指定默认值。

### 离线识别

- 相机：OpenCV 采集 → 输入适配 → ViewModel 运行流程 → 共享推理能力／Rust 推理适配 → 识别结果。
- 外部：ZeroMQ 收图 → 输入适配 → 同一个 ViewModel 运行流程与推理能力 → ZeroMQ 返回结果。

识别路径不经过 Agent，也不依赖启动 Python 训练进程。此处的 ZeroMQ 是对外识别接入，不是前后端内部通信。

## 6. 依赖与状态规则

- 核心业务通过明确接口使用执行能力，具体技术由适配实现承担，不让业务代码散落第三方调用细节。
- 外部输入或后台结果通过接口、回调或状态通知进入 ViewModel，驱动层不直接修改 View 或 ViewModel 内部状态。
- ViewModel 管理统一运行状态，可复用应用服务维护业务数据；View 展示该状态，Agent 通过统一能力接口获取或改变同一份业务事实。
- Agent 操作引发的变化需要反映到界面，不能存在“对话状态”和“按钮状态”两套互不一致的事实。
- ViewModel 负责与基础层、驱动层交互；已有非 UI 能力之间可按职责复用基础服务，但 View 不越过 ViewModel 调用它们。六层不要求每次调用逐层经过。
- 阻塞计算与等待不放在界面事件线程。具体调度方式、训练与推理是否并行及资源策略，后续再定。

## 7. 本地运行与联网边界

主程序、Codex CLI、Skills 和所需 runtime 由同一软件交付与管理。内部辅助进程不改变单主程序的产品形态，也不要求用户另行搭建服务。

沿用已经确认的联网边界：Agent 交互和初标允许调用配置的在线大模型服务并发送任务图片；训练计算在本机；生产识别可在不依赖互联网和在线 Agent 的条件下运行。

“Codex 本地内置”不被写成“当前已经支持完全离线的大模型交互”。本框架不增加本地大模型后端或额外视觉模型。

## 8. 目录分层

### 8.1 单 Cargo 包与目标目录树

Rust 侧先采用一个 Cargo 包，不拆成多成员 workspace。六层通过目录和模块边界组织，Python 训练源码作为独立的语言工程保留在 `depoly/packaging/python/` 下。

目录位置不改变架构职责：Python 训练执行仍属于驱动／适配层，私有解释器与依赖环境的管理仍属于基础层。

- Rust 主窗口导航通过 `page-requested` 绑定 MainWindowViewModel；独立 Viewer 保留本地导航回调，以便无需 Rust 宿主也可预览。纯视觉布局状态继续留在 View；ConfigViewModel 已实现但设置页参数编辑尚未绑定。

日志与配置的实现约定见 [Logger](plans/foundation/Logger.md) 和 [ConfigManager](plans/foundation/ConfigManager.md)。MainWindowViewModel 通过 `foundation::with_logging` 协调日志运行期，并调用 ConfigViewModel 初始化配置；Slint 事件循环仍在日志作用域内。内部线程、队列和生命周期守卫保留在 `logger.rs`，不另建模块；未经明确授权，不在 `src/foundation/` 新增其他文件。

### 8.1.2 可拖拽面板布局

- `ui_items/Splitter.slint` 提供统一分隔条、拖拽、方向键操作、可访问标签与尺寸上下限；`ui_items/SplitArea.slint` 作为尺寸由外层决定的分割区域。分割区域使用明确的几何边界放置面板，面板内部继续使用原有布局，避免父子尺寸推导回路。
- 主窗口包含导航与工作区、工作区与 Agent 两条竖向分隔条。初始按约 1:8:4 分配，导航至少 140px，工作区至少 540px，Agent 至少 260px；导航最小宽度优先于精确比例，剩余空间默认按 2:1 分配。
- 运行页图像与记录、模型列表与详情、预标注的描述／分析和分析／规则、逐图标注列表与画布、训练参数／效果、效果／日志及两块曲线、聊天历史与输入区域，均有相应分隔条。只有一个功能面板的页面不添加无意义分隔条，固定标题、工具栏、目录条和字段不参与拖拽。
- `ViewTypes.slint` 的 `PaneLayout` 由 `MainWindow` 在条件页面之外持有；各页面仅绑定自身的尺寸字段，切页、折叠及缩放不覆盖用户偏好。尺寸只保留到当前进程退出，不写配置文件，不调用业务服务。

### 8.1.3 统一的窗口外框与标题栏

`MainWindow` 为中央各页面提供和 Agent 一致的磨砂圆角外框及 18px 内边距。页面标题、图标按钮、分隔线和内部内容均在框内；中间工作区最小宽度调整为 540px，以保留内边距后的内容空间。

各页面与 `GlobalChat` 共用 `WorkspaceHeader`：标题行 34px、标题图标 18px、文字 1.1rem / 600、行内间距 8px，下方以 16px 间距连接 1px 分隔线。工具按钮继续使用 34×34px 的 `IconButton` 普通玻璃样式；已有选中状态保留，不改变业务回调。软件顶端 `AppHeader` 不参与此统一。

`GlassPanel.inset` 用于外框内的功能分区，弱化内层边框与阴影，Splitter、会话尺寸偏好及输入草稿保持原有职责，不新增配置字段或业务接入。

### 8.2 Python、资源与基础层的对应

| 内容 | 目录位置 | 职责归属 |
| --- | --- | --- |
| Python 训练源码 | `depoly/packaging/python/src/vision_trainer/` | 驱动／适配层中的训练执行部分 |
| Rust 调用 Python 的适配代码 | `src/drivers/` | 驱动／适配层 |
| 私有 runtime 定位、校验与管理代码 | `src/foundation/` | 基础层 |
| runtime 组装规则和版本清单 | `depoly/packaging/runtime/` | 构建与交付配置，不是环境本体 |
| 产品内 Codex 的指令与技能资源 | `src/view/resources/agent/` | Agent 运行资源，不是开发 Agent 的仓库规则 |

根目录 `AGENTS.md` 面向维护仓库的开发 Agent；`src/view/resources/agent/` 面向软件内部 Codex。不得将两者混用。

源码、真实运行环境和用户项目数据分开管理。Python 解释器、PyTorch 等完整环境是交付资源，不作为源码提交；用户图片、训练记录及模型数据的实际存放布局另行设计。目前 `depoly/packaging/python/` 仅有目录占位，没有 Python 包配置、训练代码或运行环境。

### 8.3 bin 目录约定

- `bin/` 用于归集编译结果，按 `windows/`、`linux/` 分开，避免不同平台产物混放。
- 可存放生成的主可执行文件及配套运行文件，不放源码或用户项目数据。
- 当前 Cargo 的构建结果在 `depoly/target/`，本次已将 Linux 骨架可执行文件手动归集到 `bin/linux/vision-hyper-agent`；操作说明见 README。
- 生成的 `bin/` 内容已加入 `.gitignore`。空的 `bin/` 目录不通过 Git 保留，新工作副本在归集产物时按需建立。
- 尚未配置自动归集、安装器或 Windows 构建，不能把本机骨架产物当作完整软件发行包。

### 8.4 depends 目录约定

`src/depends/` 管理第三方依赖的来源、版本说明及受控材料，当前只包含 [README](../src/depends/README.md)，没有实际依赖或下载内容。

它不替代 Cargo/Python 的依赖声明，不承担运行时环境管理，也不与 `depoly/packaging/runtime/` 的组装规则混用。下载归档、缓存和预编译材料的生成目录已按约定忽略；具体依赖接入方式及版本仍待确认。
