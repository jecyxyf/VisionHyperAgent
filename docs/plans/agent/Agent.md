- 版本：0.2 草案
- 日期：2026-09-10
- 来源：与用户的需求采访，以最后确认的要求为准。
- 本轮交付：保存需求，不实现代码、不安装运行环境、不编译 Codex。
- 状态：已确认的要求见正文；尚未决定的事项单独列出，不能擅自当作默认方案。
- 当前阶段：已确认功能职责和通信两端分工，并编写完整 API 设计草案；当前进行文档评审，尚未实现。生命周期仍是后续优先细化项，不再把其他已编写的接口描述为尚未开始设计。
- 暂缓事项：Python 相关内容暂缓讨论、细化和实现，包括执行工具、代码保存及动态接入；这是暂缓，不是取消既有需求。

## 1. 目标与定位

围绕开源 Codex 封装通用 Agent 库，供 VisionHyperAgent 及后续类似程序复用。此前“Driver 级别”表示通用接入能力，不表示把整套 Agent 放进驱动目录：当前 Agent 能力归 `src/agent/`，ZMQ 角色封装归 `src/drivers/`，宿主交互归 `src/view_model/`；不因此拆分 Cargo 包。

核心目标是：**分析用户需求，结合 Skills 决定如何处理，调用软件提供的工具，必要时生成 Rust／Python 代码，再通过固定工具接入主程序。**

Codex 负责模型交互、需求理解、代码生成和工具选择。库负责统一接入、运行管理、消息与会话管理、工具调用接口。具体业务由接入程序提供，不重新实现同类 Agent 引擎。

总体目标保留 Rust、Python 两种语言的调用入口，不规划 C++、C# 等其他语言 SDK。具体封装和发布形式仍需确定；Python 相关内容按当前安排暂缓推进。

## 2. 已确认的能力范围

本节记录总体能力目标，不表示当前同时推进全部内容；涉及 Python 的部分保留需求，暂缓讨论和实现。

| 能力 | 要求 |
| --- | --- |
| 图文对话 | 支持连续对话，一条消息可以包含文字和多张图片。 |
| Skills | 用于说明任务规则、操作步骤和工具使用方式。 |
| 需求分析与代码生成 | Codex 可以分析需求、选择已有工具，也可以根据需求生成 Rust／Python 代码。 |
| 自定义工具 | 接入程序提供真实的标注、训练、推理等功能，供 Agent 调用并返回结果。 |
| 固定代码集成工具 | 生成代码必须通过固定工具进行处理，使主程序不重启也能接入并调用新功能。 |
| 会话与历史管理 | 每个会话都属于历史记录，支持保存、查询和继续使用，不采用临时会话模式。 |
| 请求调度 | 支持串行排队、取消等待任务、停止当前任务、错误反馈和手动重试。 |

**不向模型开放 Codex 的内置执行工具**，包括通用终端命令、任意文件读取和修改等工具。执行操作通过已注册的自定义工具完成。

库内部加载用户图片、读取指定 Skills、管理配置和保存会话所需的受控文件操作，不属于向模型开放通用文件工具。

MCP、插件市场、多 Agent 编排和额外的长期经验学习，不作为本次必做能力。

## 3. 库与使用方的职责

| 部分 | 负责内容 |
| --- | --- |
| 通用 Agent 库 | Codex 接入、图文消息、Skills 接入、会话历史、任务队列、取消、事件和错误输出、自定义工具注册与调用。 |
| Codex | 理解用户需求，结合规则选择工具，生成回复或代码，并根据工具的真实结果继续处理任务。 |
| 接入程序 | 提供配置、界面、业务状态，以及实际的标注、训练、推理等工具实现。 |
| 固定代码集成工具 | 作为 Agent 与本地执行能力之间的固定入口，传递代码和执行请求并反馈结果；实际运行由本地程序负责。Python 工具入口已有确认但暂缓细化，见第 9 节。 |

库不得直接依赖 Slint、YOLO 或 VisionHyperAgent 的 `CONFIG`、`LOGGER`、`APP_PARAM` 等全局对象。

配置、日志接收方式、Skills 位置、工作目录、历史存储位置和工具实现，应由使用方提供或通过库的配置入口指定。不同程序的配置和会话应保持隔离。

通用库保留显式接收路径参数的能力；VisionHyperAgent 宿主必须按第 3.2 节已经确认的目录组装参数，不再自行选择其他默认位置。

接入 VisionHyperAgent 时，由项目侧读取已有配置，再传给库。按钮和 Agent 必须调用同一套真实业务功能，不能为聊天另写一套训练或推理实现。

### 3.2 已确认的运行时目录

“应用程序目录”指发布后主程序可执行文件所在目录，不是启动命令的当前工作目录，也不是源码仓库目录。目录名大小写固定如下：

| 内容 | 运行时位置 | 边界 |
| --- | --- | --- |
| Skills | `应用程序目录/Skill` | 本软件的产品 Skills 来源，不自动从工作目录或开发者个人目录补充 |
| 会话记录数据 | `应用程序目录/Chat` | 会话历史及其必要数据的存储根，不等于显示清空、任务重放或 Python 代码永久保存策略 |

路径由宿主定位并作为参数交给通用库，切页、切换任务工作目录或改变启动位置不能改变这两个目录。源码资源仍按项目既有目录管理，本轮不迁移资源、不创建实际 Skill／Chat 目录，也不增加设置页中的路径修改功能。

目录准备、权限检查、内部子目录与固定版本 Codex 的映射仍需在实现前明确；路径本身已确认，不能再作为任意默认值处理。缺失、不可读或不可写必须明确报告，不得静默改用系统用户目录、自动提权或伪造加载／保存成功。是否有其他 Codex 内部数据需要独立位置应另行说明，不能把整个 Codex Home、无关日志或凭据默认等同于 Chat。

## 4. 模型连接

- 按 OpenAI Responses API 兼容方式接入，不把仅兼容 Chat Completions 的服务默认视为可用。
- VisionHyperAgent 继续使用现有 `CONFIG.agent` 中的 `base_url`、`api_key`、`model`，不重复增加连接配置。
- 所选模型和服务需要支持本期使用的图片输入与工具调用能力，实际兼容性仍需验证。
- KEY 不得进入聊天内容、模型提示、日志或诊断展示，不继承或修改开发者个人的 Codex 配置。
- 配置缺失、服务不兼容、鉴权失败或网络错误必须明确报告，不能伪装成功或擅自更换模型。

## 5. 运行与线程通信

已选择的方向是：**Codex 运行时嵌入主进程，Agent 在独立后台线程中运行。**

- Agent 随使用方程序启动，在后台初始化，不以连接模型成功作为主界面启动前提。
- UI 只负责交互与显示，不同步等待模型、工具执行或线程收发。
- 本项目线程间使用 ZeroMQ `inproc` 通信，面向 Windows、Linux；共享 Context，各线程按相应 Socket 的线程规则使用自己的连接。
- ZMQ 负责传输，库负责任务状态与排队，不能把 ZMQ 内部缓冲直接当作完整的业务任务队列。
- 取消控制不能排在普通任务后面等待，也不能因流式输出堵塞而失去响应。
- 不修改 Codex 内部已有的通信机制，不提前建设全软件消息总线。
- 程序关闭时需要结束 Agent 运行、处理任务状态、保存必要历史并释放资源。

宿主通过 `Agent` 和各 Manager 使用功能，不直接操作 Socket。`AgentTransport` 区分 Host 与 Runtime 两端，分别使用 `ZmqClient` 和 `ZmqServer`；两端共享同一底层 Context，但不能共同使用一个 Socket。UI 与 ViewModel 通过 View 绑定交互，不使用 ZeroMQ。

命令响应、异步事件和业务终态分开：取得 TaskId 仅代表受理，收到模型终态也不代表宿主工具副作用可以回滚。整体 AgentState 由 Agent 的生命周期协调逻辑根据两端通信与后台运行的真实结果维护，Runtime 的局部结束不能单独代表整条链路已经关闭。

独立线程可以避免将耗时工作直接放到 UI 上，但不等于进程级隔离。仍需防止长时间占锁、阻塞调用和过量刷新；不能承诺任意生成代码在同进程内执行都不会影响主程序。

“单进程”主要指 Agent 引擎的接入方式。固定工具是否使用编译器、Python 执行器或其他辅助进程，尚未确定，不能预先承诺整个系统永远不产生子进程。

断网或 Agent 不可用时，不应阻止主程序及其他本地功能运行。连接远端模型的对话仍需要网络；未来生产推理须保持既定的离线能力。

## 6. 图文交互要求

以下是接入 VisionHyperAgent 时需要满足的交互要求，不要求通用库包含 Slint 控件。

- 图片可以通过文件选择、拖拽和剪贴板粘贴加入消息。
- 一段文字可以附带多张图片；发送前展示缩略图，并允许移除选错的图片。
- 图片选择、剪贴板操作和缩略图界面由使用方实现，库提供对应的图文输入能力。
- 回复边生成边显示，用户可以停止当前回复。
- 回复支持 Markdown 内容；标题、列表、表格和代码块的渲染由使用方界面完成。
- 生成期间可以继续编辑并发送下一条消息，新消息进入等待队列，不并行执行。
- 不随意承诺无限图片输入。图片格式、大小和数量限制需要结合所选 Codex、模型服务与资源保护方案确定；不支持或超限时明确提示。

## 7. 队列、取消和失败处理

同一执行队列一次只处理一条用户请求，按发送顺序依次处理。

| 情况 | 已确认行为 |
| --- | --- |
| 正在回复时发送新消息 | 新消息进入等待队列。 |
| 取消尚未执行的消息 | 不再执行该消息，不发送给模型。 |
| 停止当前消息 | 中断当前请求，结束后继续处理后续队列。 |
| 当前请求失败 | 显示错误，保留失败消息和图片，后续队列继续执行。 |
| 重试失败消息 | 由用户手动发起，库不自动重新发送整条失败消息。 |
| 清空聊天显示 | 只影响界面记录，不停止当前任务，不重置当前会话上下文，不清空未发送的草稿。 |

取消必须准确对应任务，不能误停下一条请求。区分“正在停止”和“已经结束”，以实际执行结果更新状态，避免晚到的回复混入其他任务。

停止 Agent 不等于自动停止已启动的业务工具。长时间运行的工具需要支持取消或明确报告不能取消的阶段；已写入、已加载或已经产生的结果不应被描述为自动回滚。

工具失败应返回真实错误，供 Codex 继续判断；如果整条用户请求最终失败，再按上表处理。库不叠加整条消息的自动重试，Codex 和网络层自身的重试行为需要在后续技术方案中核查清楚。

这里的队列只管理 Agent 对话请求，不接管宿主训练等业务任务。通信层等待响应的调用表、用户请求队列、Agent 事件缓存和 View 更新缓存是不同对象，不能用其中一个的容量或结束状态代表全部链路。

## 8. 会话与历史

本节以用户最后要求为准，替代采访早期“不跨启动保留会话”的决定。

- 每个会话都持久化管理，不使用临时会话作为本期模式。
- 在 VisionHyperAgent 中，会话记录数据根固定为 `应用程序目录/Chat`；具体历史、索引和附件的内部组织仍需核查所选 Codex，不改变已确认的根目录。
- 优先复用 Codex 已有的会话创建、查询、读取和恢复能力，不另造一套 Agent 会话引擎。
- 保存历史是为了查看和继续工作，不自动扩展成从聊天中提炼长期经验的系统。
- “清空当前聊天显示”“删除历史会话”“取消任务”是不同操作，不能互相替代。
- 历史会话中的图片及相关资源必须考虑后续可用性，不能只保存一个可能失效的临时路径。
- 尚未进入 Codex 的排队消息、失败记录和取消状态如何与原生历史对应，需要在设计中补齐。
- 重启后如何处理未完成任务、是否恢复上次选中的会话，尚未确认。保存历史不等于允许自动重放旧任务。

## 9. 生成代码与运行时接入

已确认的目标是：生成 Rust／Python 代码后，通过固定工具在运行期间接入，主程序无需重启即可调用新功能。

**职责分工：Agent 提供代码和调用请求，本地程序负责实际运行，并返回真实结果、进度或错误。生成代码不等于代码已经运行，更不等于执行成功。**

```text
用户提出需求
→ Codex 结合 Skills 分析
→ 调用现有工具，或生成 Rust／Python 代码
→ 通过固定工具将代码和请求提交给本地程序
→ 本地程序校验并调用本地执行组件处理和运行
→ 主程序在无需重启的情况下调用接入的新功能
→ 真实执行结果返回给 Codex 和使用方
```

- 不通过开放 Codex 通用终端或任意文件修改工具实现代码集成。
- 生成代码只是输入，不能直接当作可信或已经可执行的功能。
- 固定工具需要处理接口约束、错误、权限和取消；编译、加载失败不能伪装成功。
- 具体采用何种 Rust 模块加载方式、Python 运行方式，以及是否需要隔离执行，尚未确定。
- 固定工具虽然入口受控，但如果接受任意代码执行，仍存在访问文件、启动进程、占用资源或影响主程序的风险，不能把“禁用内置工具”当作安全保证。

### Python 相关确认与暂缓范围

以下确认保留为后续恢复讨论的依据，不在当前阶段继续细化或实现：

- Agent 库提供对接本地 Python 执行能力的固定工具入口；Agent 提供代码，本地程序调用执行器运行，不由 Agent 管理解释器或运行环境。
- Python 代码交给软件管理的本机 Python 解释器执行，不要求用户安排单独的编译步骤，不转移到云端运行。
- Agent 提供的 Python 代码默认不做永久保留；只有用户明确提出要求时，才永久保存。
- 临时代码的清理时机、聊天历史中代码文本的保留方式，以及具体工具接口、封装和执行方式，均暂缓讨论。不能推定运行结束立即删除，也不能擅自改变已确认的会话历史持久化要求。

| 资源与超时 | 分别明确请求队列、调用关联、Agent 事件与 View 更新的容量，图片限制、工具时限及退出等待策略；不能因上游部分通道有界就宣称端到端有界，不预设未经确认的数值。 |
| 技术兼容性 | Codex 进程内组件与本项目的构建兼容性；禁用内置工具后 Skills 和自定义工具的完整路径；Windows/Linux 的实际表现。 |

## 11. 后续验收目标

这是未来实现的验收方向，本次仅编写需求文档，不代表以下项目已经通过：

1. Rust 和 Python 使用方能接入同一套 Agent 能力，库不依赖具体 UI 或 VisionHyperAgent 的全局对象。
2. 能完成文字、多图、连续对话、流式回复和停止操作。
3. Skills 能用于指导任务，执行仅经过已注册工具，不把未执行的行为报告为成功。
4. 能注册业务工具，接收调用、返回真实结果，并处理工具失败与取消。
5. 排队、停止、失败继续、手动重试和清空显示符合已确认规则。
6. 会话可以保存、查询和继续，图片资源与历史状态保持一致。
7. 在完整接入链路中，生成代码能够通过固定工具投入使用，主程序无需重启；固定工具的验收归属需先确认提供方。
8. UI 不因 Agent 工作而同步阻塞；网络或 Agent 故障不阻止其他本地功能运行。
9. Windows/Linux 及 Rust/Python 接口需要分别验证，不能以源码中存在接口代替实际通过。
