# Logger 日志设计

- 日期：2026-09-08
- 状态：已改为异步写入并接入主程序自动收尾；Linux 临时功能验证与 Windows 目标编译检查通过，Windows 尚未实机测试。
- 范围：Rust 基础层及主程序最小日志生命周期托管，日志模块不依赖 Slint、Agent、配置或训练业务；主程序现已在托管作用域中运行 Slint 事件循环。

## 1. 类型与目录

- 类型：`Logger`。
- 全局单例：`LOGGER`，由 `src/foundation/mod.rs` 统一导出。
- 实现文件：`src/foundation/logger.rs`。
- 路径定位和共享错误上下文放在 `src/foundation/mod.rs`，不新增其他基础层源码文件。
- 配置设计：[ConfigManager](ConfigManager.md)。

使用线程安全的静态初始化、有界队列和单个后台写入线程，不使用 `static mut`。单例与并发保证限于当前进程，不把它当作跨进程锁。后台状态及生命周期守卫均为 `logger.rs` 内部实现，不新增源码文件。

## 2. 保存位置与文件管理

- 固定保存到**可执行程序所在目录**下的 `logs/`，不随启动工作目录改变。
- 按日志产生时的系统本地日期，一天一个 UTF-8 文本文件：`YYYY-MM-DD.log`；不是后台处理时才决定日期。
- 同一天重启继续追加，不覆盖当天已有日志。
- 保留最近 90 个自然日，包含当天；不是简单保留最近 90 个文件。
- 初始化及跨日写入时清理过期日志，只处理本模块命名规则匹配的普通文件，不遍历其他目录或删除无关文件。
- 不按大小拆分，以保持一天一个文件的约定。
- 只写文件，不输出终端，不隐式回退到其他目录。

## 3. 级别与内容

提供且默认记录全部四个级别：`debug`、`info`、`warning`、`error`。不增加 `trace`，首版不把日志级别加入 `config.json`。

每条记录包含：

| 字段 | 约定 |
| --- | --- |
| 时间 | 系统本地时间，精确到毫秒 |
| 级别 | `DEBUG`、`INFO`、`WARNING`、`ERROR` |
| 模块 | 调用方提供的模块标识 |
| 源码位置 | 具体源码文件及行号，自动捕获业务调用位置 |
| 消息／原因 | 具体事件或经过脱敏的错误原因 |

格式示例，以下不是实际运行记录：

```text
2026-09-08 14:32:18.427 [ERROR] [config] [src/foundation/config_manager.rs:128] 读取 config.json 失败；原因：权限不足
```

四个级别均在调用线程中捕获日志调用处的源码文件、行号和时间，入队后不改为后台写入位置。`error()` 与其他级别使用相同格式，原因直接传入文本；不再提供 `error_with_context()`。跨层错误如需附带原始位置，可将已脱敏的 `FoundationError` 格式化为消息，其文本包含错误来源；仅有普通字符串时不猜测原始出错行。

消息可以包含相关数据路径、JSON 行列和原因链，明确区分数据位置与日志调用位置。换行等控制字符进行转义，使每条记录保持独立、可识别。

## 4. 调用接口

`LOGGER` 仅公开五个方法：

- `LOGGER.init()`：同步检查目录和文件并启动后台线程；运行中重复调用不重置队列。
- `LOGGER.debug(module, message)`。
- `LOGGER.info(module, message)`。
- `LOGGER.warning(module, message)`。
- `LOGGER.error(module, message)`。

所有方法返回 `Result<()>`。四级方法成功仅表示已入队，不表示已完成写入。当前队列容量为 4096 条，是内部实现常量，不加入 `config.json`；队列满返回 `QueueFull`，不等待磁盘、不静默丢弃。调用方必须处理错误，未成功入队的记录不能算已保存。

初始化前、退出阶段或退出后写入返回错误。后台 I/O 失败会停止本轮写入，后续调用返回 `WorkerStopped` 并附带已知诊断；入口收尾返回实际后台错误。磁盘满、目录权限等原因导致日志文件不可写时，不能再保证把该故障写入同一文件，也不递归写日志或回退到终端。

### 自动退出收尾

主程序使用 `foundation::with_logging(|| { ... })` 包住整个运行期。它持有内部生命周期守卫，正常返回（包括 `Result::Err`）时自动停止接收新记录，等待队列读完、文件同步及后台线程结束；不采用超时丢弃尾部日志的策略。不公开 `flush()` 或 `shutdown()`，业务代码无需手动刷新或关闭。

闭包返回的业务错误会通过 `error()` 写成文本。`with_logging()` 只有业务执行与日志收尾均成功才返回成功；当前 `main.rs` 在失败时返回非零退出码。

```rust
use vision_hyper_agent::foundation::{self, LOGGER};

fn main() -> foundation::Result<()> {
    foundation::with_logging(|| {
        LOGGER.info("app", "程序启动")?;
        // 在这里运行应用；结束业务后台线程后再返回。
        LOGGER.error("inference", "模型加载失败；原因：文件不存在")?;
        Ok(())
    })
}
```

单独调用 `LOGGER.init()` 不会托管进程退出，不能用它替代入口作用域。暂不支持嵌套或并发托管；正常收尾后可重新建立作用域并继续追加。当前 Slint 事件循环已位于此作用域内，未来业务线程回收也必须位于此作用域内；业务线程不能在作用域返回后继续写日志。

## 5. 安全与技术边界

- 不输出 Agent KEY、完整配置 JSON、认证头或用户图片内容。
- 配置对象的调试输出脱敏；调用方不得主动把 KEY 拼接进消息。
- 配置解析错误使用安全的错误分类、位置与上下文，避免原因链泄漏配置原文。
- 采用 Rust 标准库管理单例、线程、队列、锁与文件，使用 `chrono 0.4.45` 处理本地日期时间；未新增依赖，版本与传递依赖由 `Cargo.lock` 固定。
- 日志属于运行产物，不提交 Git。
- 正常收尾保证在文件系统可写、未发生 I/O 故障的前提下，不因队列残留丢失已接收记录；不承诺跨进程并发写入、吞吐指标或故障存储下绝对持久性。
- panic 展开时守卫尽力等待后台完成；强制终止、默认信号终止、`abort`、`process::exit` 或断电会绕过正常收尾，不能承诺零丢失。不得在正常关闭路径直接调用 `process::exit`。

## 6. 验证要求

覆盖四个级别、入队时的时间与源码位置、原因文本、多线程完整记录、同日追加、跨日切换、90 天边界、无关文件保护、不可写路径、重复初始化、无终端日志和敏感信息不泄漏；增加队列满、后台失败、退出等待、返回错误、panic 展开、嵌套托管拒绝和退出期间拒绝新写入的检查。

文件与日期测试使用临时目录和可控时间，不依赖 GPU、相机、网络或真实 KEY。

## 7. 实现与验证

源码目录严格保持三个文件，`ErrorContext`、`SourceLocation`、`FoundationError` 与可执行目录定位都放在 `mod.rs`。错误上下文由产生错误的代码创建并向上传递；JSON 类型错误不保留可能含 KEY 的 serde 原始错误文本。

本轮使用临时测试验证异步行为：21 项白盒用例通过，重复 20 轮共 420 次执行通过；独立进程与接口检查 36 项通过（含 20 轮并发退出、3 项已删除接口的编译拒绝检查）。并发退出单轮 16,001 条记录，20 轮共 320,020 条全部写入、无缺失或重复。受控暂停后台线程时，入队不执行文件写入，入口确实等待线程完成后返回。Windows 当前仅通过目标编译链接检查。
