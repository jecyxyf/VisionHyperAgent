# Logger 日志设计

- 日期：2026-09-08
- 状态：已按确认方案实现；Linux 测试和 Windows 目标编译检查通过，Windows 尚未实机测试。
- 范围：只实现 Rust 基础层，不接入 Slint、Agent 或训练业务。

## 1. 类型与目录

- 类型：`Logger`。
- 全局单例：`LOGGER`，由 `src/foundation/mod.rs` 统一导出。
- 实现文件：`src/foundation/logger.rs`。
- 路径定位和共享错误上下文放在 `src/foundation/mod.rs`，不新增其他基础层源码文件。
- 配置设计：[ConfigManager](ConfigManager.md)。

使用线程安全的静态初始化与内部锁，不使用 `static mut`。单例与并发保证限于当前进程，不把它当作跨进程锁。

## 2. 保存位置与文件管理

- 固定保存到**可执行程序所在目录**下的 `logs/`，不随启动工作目录改变。
- 按系统本地日期，一天一个 UTF-8 文本文件：`YYYY-MM-DD.log`。
- 同一天重启继续追加，不覆盖当天已有日志。
- 保留最近 90 个自然日，包含当天；不是简单保留最近 90 个文件。
- 初始化及跨日写入时清理过期日志，只处理本模块命名规则匹配的普通文件，不遍历其他目录或删除无关文件。
- 不按大小拆分，以保持一天一个文件的约定。
- 只写文件，不输出终端，不隐式回退到其他目录。

## 3. 级别与内容

提供且默认记录全部四个级别：`debug`、`info`、`warning`、`error`。不增加 `trace`，首版不把日志级别加入 `config.json`。

每条记录包含：

| 字段 | 约定 |
| --- | --- |
| 时间 | 系统本地时间，精确到毫秒 |
| 级别 | `DEBUG`、`INFO`、`WARNING`、`ERROR` |
| 模块 | 调用方提供的模块标识 |
| 源码位置 | 具体源码文件及行号，自动捕获业务调用位置 |
| 消息／原因 | 具体事件或经过脱敏的错误原因 |

格式示例，以下不是实际运行记录：

```text
2026-09-08 14:32:18.427 [ERROR] [config] [src/foundation/config_manager.rs:128] 读取 config.json 失败；原因：权限不足
```

源码位置不能固定指向 `logger.rs` 内部。普通日志捕获日志调用处；跨层错误通过携带来源信息的错误上下文保留最初的文件、行号和原因链。没有来源信息的字符串或外部错误，不猜测其原始出错行。

涉及数据文件时记录相关路径；JSON 解析错误额外携带 JSON 内的行号、列号，明确区分数据位置与 Rust 源码位置。换行等控制字符进行转义，使每条记录保持独立、可识别。

## 4. 调用接口

已提供：

- `LOGGER.init()`：初始化目录和文件；成功初始化后重复调用不重复打开或重置状态。
- `LOGGER.debug(module, message)`。
- `LOGGER.info(module, message)`。
- `LOGGER.warning(module, message)`。
- `LOGGER.error(module, message)`。
- `LOGGER.error_with_context(module, message, context)`：记录带原始来源和原因链的错误。
- `LOGGER.flush()`：显式刷新。

初始化与写入接口返回 `Result`。初始化前调用、目录不可写、文件打开或写入失败、清理失败、锁异常等，必须向调用方返回可检查的错误；不吞错、不递归记录日志组件自身的写入错误。

首版采用同步写入和进程内互斥，保证同一进程的多线程记录不交错；暂不建立异步日志队列。

## 5. 安全与技术边界

- 不输出 Agent KEY、完整配置 JSON、认证头或用户图片内容。
- 配置对象的调试输出脱敏；调用方不得主动把 KEY 拼接进消息。
- 配置解析错误使用安全的错误分类、位置与上下文，避免原因链泄漏配置原文。
- 采用 Rust 标准库管理单例、锁与文件，使用 `chrono` 处理本地日期时间；使用 `chrono 0.4.45`，传递依赖由 `Cargo.lock` 固定。
- 日志属于运行产物，不提交 Git。
- 本文不承诺跨进程并发写入、异步吞吐指标或断电后的绝对持久性。

## 6. 验证要求

覆盖四个级别、时间与源码位置、错误原因链、多线程完整记录、同日追加、跨日切换、90 天边界、无关文件保护、不可写路径、重复初始化、无终端输出和敏感信息不泄漏。

文件与日期测试使用临时目录和可控时间，不依赖 GPU、相机、网络或真实 KEY。

## 7. 实现与验证

源码目录严格保持三个文件，`ErrorContext`、`SourceLocation`、`FoundationError` 与可执行目录定位都放在 `mod.rs`。错误上下文由产生错误的代码创建并向上传递；JSON 类型错误不保留可能含 KEY 的 serde 原始错误文本。

已覆盖同日重启追加、本地日期跨日、90 天边界、无关文件／目录／符号链接保护、多线程整行写入、调用文件行号、原因链、控制字符转义和失败返回。子进程测试验证改变工作目录后仍写在可执行目录，且日志标记不进入终端。Windows 当前仅通过目标编译检查。

## 一键功能测试

从仓库根目录运行 `python3 depoly/tests/test_foundation.py`。脚本不依赖 Slint、GPU、在线服务或真实 KEY；除单元测试外，还复制测试可执行文件到临时目录，以全新进程实际调用 `LOGGER`、`CONFIG`，检查磁盘文件和保护行为。底层源码仍严格限定为三个文件。
