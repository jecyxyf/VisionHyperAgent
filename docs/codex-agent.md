## 1. 核心约定

**Codex 的启动和停止由后端 `server` 统一控制。**

- 主程序启动时，后端自动启动一个属于本应用的 Codex App Server。
- `CodexAgent` 只负责 WebSocket 连接、协议调用和事件接收，不自行启动或结束进程。
- 主程序退出时，后端中断任务、断开连接、停止自己启动的 Codex，再完成服务退出。
- 关闭或刷新网页不影响 Codex 进程；前端“停止”仅中断当前回合。
- 保持现有目录结构和前端布局，不引入额外的 Python 常驻服务。

```text
现有 Agent 面板
      ↕ WebSocket / 附件 HTTP 上传
Rust server（应用运行时、进程所有权、业务接口）
      ├── CodexProcess（启动、监控、结束子进程）
      └── CodexAgent（WebSocket / JSON-RPC 客户端）
                    ↕ 本机 WebSocket
              Codex App Server
                    ↕ 模型 HTTP API
              配置的模型服务
```

这里有两条不同的 WebSocket 连接。浏览器不直接连接 Codex，也不持有模型服务密钥。

## 2. 职责与代码边界

| 位置 | 负责 | 不负责 |
| --- | --- | --- |
| `server` | 应用配置、持有进程和客户端、启动与退出编排、前端接口、附件落盘、状态同步 | 不重复实现 Codex 协议传输 |
| `codex_agent/process.rs` | 提供跨平台进程操作，供 `server` 调用 | 不自动启动、不由前端直接调用 |
| `codex_agent` 中的 `CodexAgent` | 连接与握手、请求关联、会话和回合接口、通知和服务端请求 | 不创建或杀死进程、不上传文件、不保存业务数据 |
| `common` | 已有全局日志 | 不新增第二套日志单例 |
| 前端 Agent 组件 | 输入、流式显示、模型/Effort、会话、附件、审批交互 | 不管理 Codex 进程、不直连外部模型 |

通信库内部按配置、类型、协议传输、客户端、进程工具、错误拆分文件，全部留在现有 crate 内。
不改动 `source/backend/depends/codex` 的源代码。

## 3. 后端运行时与进程生命周期

### 3.1 启动

1. 初始化全局日志，读取本应用配置。
2. 启动本地 HTTP 服务和托盘，使启动中的状态及错误可观察。
3. 后端启动 Codex App Server，只监听 `127.0.0.1`。
4. 后端持续读取子进程 stdout/stderr，避免管道写满导致子进程卡死。
5. `CodexAgent` 在启动超时范围内连接，完成 `initialize` 请求及 `initialized` 通知。
6. 握手成功后才将 Agent 状态标为可用，并加载模型、会话等信息。

Codex 可执行文件路径可配置；优先使用配置路径，其次应用随附的可执行文件，最后使用系统 PATH。
Windows 运行需要实际可用的 Windows Codex 可执行文件；交叉编译主程序不等于已经打包该依赖。
Codex 使用后端运行期自动分配的独立本机随机端口；端口冲突自动换端口重试，子进程其他原因提前退出必须明确报错，不能误连其他实例。

缺少 Codex、密钥或启动失败时，保留托盘和网页，显示可操作的错误；不能假装 Agent 已连接。
进程意外退出后，后端更新失败状态；通信层的重连不能擅自重启进程。

### 3.2 退出

```text
托盘退出 / 后端主动关闭
  → 停止接受新的 Agent 任务
  → 对活动回合发出中断请求（有超时）
  → 关闭浏览器 WebSocket 和 Codex WebSocket，结束后台收发任务
  → 后端请求 Codex 退出，超时后强制结束并回收
  → HTTP 服务和运行时结束
  → 托盘移除，主程序退出
```

中断失败或网络断开不能跳过子进程清理。HTTP 优雅退出也不能无限等待长连接。
启动中途失败时同样清理已经创建的进程和后台任务。

防孤儿机制：

- Linux：检查父进程死亡信号设置是否成功，处理设置过程中的父进程退出竞态；正常关闭时清理自有进程组。
- Windows：后端持有配置了 `KILL_ON_JOB_CLOSE` 的 Job Object，加入失败必须回收子进程并报错，不能忽略错误。
- 只处理本应用创建并持有的进程，禁止按进程名批量结束其他 Codex 实例。

本轮以 Linux 运行验收和 Windows 构建/进程逻辑测试为目标；Windows 实机退出效果仍需在 Windows 上验证。

## 4. CodexAgent 通信设计

连接状态与进程状态分开表达：

```text
连接：disconnected → connecting → initializing → ready
      ready → reconnecting → initializing → ready
      任意连接阶段 → disconnecting → disconnected
      失败 → error

进程：stopped → starting → running → stopping → stopped
      启动或运行失败 → error
```

- 使用本机版本协议的字段、请求 ID 和消息结构，不把它当成普通模型聊天 API。
- 每个请求分配唯一 ID，通过等待表关联响应，支持并发请求及超时清理。
- 区分响应、通知、服务端请求；不能只读取文本增量而忽略审批。
- 接收循环不能被等待用户审批或某个慢请求阻塞。
- 处理 Ping/Pong、Close、格式错误、连接错误及未识别消息。
- 断线时及时结束待处理请求；重连后重新握手并同步会话状态。
- **不自动重放 `turn/start` 等可能产生副作用的请求。** 超时不等于服务端没有执行。
- 通道有容量边界；事件丢失或消费者落后时要求状态重同步，不能静默形成错误的聊天记录。
- `disconnect()` 要释放连接和任务，但绝不停止 Codex 进程。

### 对外接口与协议方法

| 接口职责 | 协议方法 |
| --- | --- |
| `connect` / `disconnect` / `status` / `subscribe_events` | 连接管理与事件订阅 |
| 初始化 | `initialize`、`initialized` |
| 模型列表 | `model/list` |
| 创建、恢复、列表、读取会话 | `thread/start`、`thread/resume`、`thread/list`、`thread/read` |
| 归档会话 / 释放未提交草稿 | `thread/archive`、`thread/unsubscribe` |
| 发送与中断回合 | `turn/start`、`turn/interrupt` |
| 清理本回合后台命令 | `thread/backgroundTerminals/list`、`thread/backgroundTerminals/terminate`（实验性接口，后端显式启用） |
| 技能列表 | `skills/list` |
| 回答审批或用户输入请求 | 对原服务端请求 ID 返回对应类型的响应 |

前端只访问后端定义的业务方法，不允许透传任意 Codex JSON-RPC 方法。
使用结构化配置、请求、响应、事件与错误；对未知扩展字段保持兼容，但不绕过方法白名单。

## 5. 事件与审批

| 事件来源 | 对前端的含义 |
| --- | --- |
| 连接、进程状态变化 | 启动中、就绪、重连中、失败、停止 |
| `thread/started` | 会话已创建 |
| `turn/started` | 回合已开始 |
| `item/agentMessage/delta` | 助手文本增量 |
| 工具执行及 `item/completed` | 工具状态、最终消息项 |
| `turn/completed` | 依据实际状态区分成功、失败、中断 |
| Codex 错误、传输错误 | 可展示的错误和关联会话/回合 |
| 命令执行、文件修改审批请求 | 待用户允许或拒绝的交互 |
| 工具请求用户输入 | 在会话中显示问题并返回答案 |

审批卡片放在现有聊天区域，不改变面板总体布局。
未识别的请求、超时或无法交互的审批不得默认允许。
测试工具能力不通过全局关闭沙箱、跳过审批来实现；仅在隔离测试目录使用必要权限。

## 6. 前端接入及交互语义

移除当前模拟会话和定时返回“Agent 未连接”的逻辑，接入真实后端状态。

| 控件 | 接入后的行为 |
| --- | --- |
| 发送 | 提交文本、已上传附件、模型、Effort 和当前会话；显示待发送/已接受/失败状态 |
| 消息区域 | 区分用户、助手、系统和工具信息，持续追加流式结果 |
| 停止 | 中断当前会话的当前回合；等待实际中断结果，不结束 Codex |
| 模型选择 | 显示后端配置的模型及可用模型信息，包含本轮测试模型 `MiniMax-M3` |
| Effort | 保留现有六个选项；能力已知时标明限制，不支持时明确报错，不静默替换参数 |
| 历史 | 从 Codex 加载、分页读取，支持创建、恢复与归档 |
| 清空 | 开始一个新会话，不沿用旧上下文，也不批量删除历史 |
| 历史删除 | 本轮采用归档，并在操作提示中明确语义，不执行不可逆的底层文件删除 |
| 拖拽附件 | 上传后使用后端生成的附件 ID；发送前可以移除，不新增上传按钮 |

补充约束：

- 同一会话同时只提交一个活动回合，防止重复点击和重复发送。
- 会话和回合事件携带标识，切换历史时不能把其他会话的增量写入当前会话。
- 页面刷新或重连后重新读取状态，不自动发送旧输入；前端断开不清除后端任务。
- 请求失败不能直接丢弃草稿和附件；取消订阅时清理监听器、心跳与重连定时器。
- 模型返回的内容按文本或安全渲染方式展示，不直接执行模型输出的 HTML。

## 7. 附件和工作目录

- 上传由 `server` 处理；`CodexAgent` 只接收已经准备好的输入描述。
- 后端生成存储名称，不能把浏览器提供的文件名或路径直接作为写入路径。
- 上传落在应用管理的目录，设置文件大小及请求体限制，处理失败后的残留文件。
- 文件路径引用必须属于当前应用/会话已登记的附件，禁止客户端任意指定服务器文件。
- 普通文件通过工作区内的文件引用供 Agent 使用，不把文件名当作“文件已经上传”。
- 图片仅在所选模型支持时按图片输入发送；无法确认支持或模型拒绝时明确提示，不声称图片已被理解。
- 工作目录由后端配置。开发测试使用专用临时目录，不发送本仓库源码或用户其他目录内容给测试模型。

## 8. 配置、凭据与本机访问

- 程序继续仅监听 `127.0.0.1`；前端 HTTP/WS 入口校验来源，避免任意外部网页驱动本机 Agent。
- 应用使用独立的 `CODEX_HOME`，保存在应用管理的数据目录中，不修改用户的 `~/.codex`。
- Codex 路径、工作目录、模型、模型服务地址及超时由后端配置，不写死在组件中。
- 开发测试密钥使用环境变量注入；需要本机持久配置时，只放在被 Git 忽略且权限受限的私有配置中。
- 源码及示例配置只包含占位符。密钥不放进命令行参数、前端响应、日志、测试快照或提交记录。
- 模型服务的 HTTP 和本机 WebSocket 是不同连接；使用自定义模型不等于绕过 Codex 直接调用聊天 API。
- 用户提供的测试服务为 HTTP，传输未加密；仅作为明确授权的测试入口，正式部署优先使用 HTTPS。

本轮测试模型固定为 `MiniMax-M3`，不得悄悄切换到其他模型。

## 9. 日志

复用 `source/backend/common` 的全局单例及既有格式：

- 记录进程创建/退出、PID、连接状态、握手、方法名、请求编号、耗时、超时、重连和清理结果。
- 错误日志关联会话和回合，方便从前端错误定位后台问题。
- 不记录认证头、密钥、完整配置、用户输入、模型正文和附件内容。
- 子进程输出须脱敏并限制长度，不将原始敏感错误体无条件写入日志或返回前端。
- UI 收到的是结构化错误，不是进程输出或内部堆栈全文。

## 10. 实施顺序

1. 实现并测试 WebSocket 客户端、初始化、请求关联、事件及基础业务接口。
2. 完善进程工具，由后端运行时持有并接入启动、失败回收、监控和退出流程。
3. 添加前端业务 WebSocket、状态同步及附件 HTTP 接口。
4. 保持现有布局，接通聊天、停止、模型/Effort、会话、附件和审批。
5. 使用隔离目录与测试模型完成端到端验证，再构建 Linux / Windows 产物。

以上步骤属于同一条功能链路；仅库编译通过或后端连上端口，不算本轮完成。

## 12. 实施补充

- 当前回合停止同时清理其已转后台的命令，不结束 Codex 或其他回合的后台命令。
- MiniMax-M3 测试服务需要显式 Chat Completions 兼容模式；该兼容层位于同一个 Rust 后端，不增加进程、不修改 Codex 源码、不绕过审批。
- 本次已验证该服务的图片输入和合成色块识别，启用需设置 `supports_images = true`；未确认能力的模型仍明确拒绝图片输入。
- Windows 项的通过范围是逻辑故障测试及交叉编译，**不包含 Windows 实机验证**。完整证据和限制见 `codex-agent-test-report.md`。
