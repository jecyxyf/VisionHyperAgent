## 1. 概述

### 1.1 软件定位

VisionHyperAgent 是本地优先的视觉数据标注与训练工具。首版围绕实例分割闭环建设：用户导入图片、通过 Agent 确认标注规则、人工完成实例标注、生成内部数据集、在本机 GPU 上训练和评估 Mask R-CNN 模型，并使用新图片进行推理测试。

产品采用本地绿色桌面运行形态：Rust 宿主进程负责本地 HTTP/WebSocket 服务、系统托盘、浏览器入口、配置、日志、任务和子进程生命周期；浏览器前端负责交互和可视化；Python ML Worker 只承担训练、评估和推理等计算密集型任务。在线模型服务只用于 Agent 的自然语言理解与建议，不参与首版自动预标注。

### 1.2 核心目标

| 目标 | 技术策略 | 验收口径 |
| --- | --- | --- |
| 完整实例分割闭环 | 前端标注、后端数据管理、Python Worker 训练评估推理分层协作 | 从图片导入到新图片推理测试全流程可运行 |
| 本地数据优先 | 项目、图片、标注、数据集、模型和记录均保存在本地项目目录 | 不依赖公网服务即可管理项目和已完成产物 |
| Agent 主导辅助 | 沿用 Rust Codex Agent 模块接入用户配置的模型服务 | 支持规则生成、训练建议、问题分析和阶段计划确认 |
| 人工标注可信 | 首版不接入 Segment Anything 或其他自动预标注模型 | Agent 只生成规则和建议，不直接生成或修改遮罩 |
| GPU 任务可控 | ML Worker 独立进程执行训练、评估和推理，宿主统一调度和回收 | 支持进度、停止、异常报告和无残留进程退出 |
| 跨平台绿色交付 | Windows 产物输出为 bin/win/ 下的 zip；Linux 产物输出到 bin/linux/，目录本身即绿色软件目录 | Windows 解压后可直接启动；Linux 直接进入 bin/linux/ 启动 |
| 可测试可维护 | 前后端与 ML Worker 通过明确协议隔离，测试分层执行 | Rust、前端、Python 单元测试和关键集成测试可重复运行 |

### 1.3 技术栈

| 类别 | 选型 | 说明 |
| --- | --- | --- |
| 前端框架 | Svelte 5 + TypeScript + Vite | 沿用现有前端工程，保留轻量、编译时优化和组件化开发方式 |
| 标注画布 | Canvas 2D | 面向 2D 实例遮罩绘制、缩放和平移，不引入 Three.js |
| 本地宿主 | Rust 2021 + Tokio | 负责进程生命周期、任务调度、本地服务和跨平台桌面能力 |
| HTTP / WebSocket 服务 | axum | 提供静态资源、REST API 和实时事件推送 |
| 桌面集成 | tray-icon + tao + webbrowser | 提供托盘、事件循环和自动打开本地界面能力 |
| 本地元数据 | SQLite + SQLx | 使用嵌入式本地数据库文件，不启动数据库服务；管理项目、图片、标注、数据集、训练、评估和推理记录 |
| 项目文件 | 本地项目目录 + JSON / PNG 等文件 | 大文件走目录：原图只读保存，遮罩、数据集清单、模型和结果按版本落盘；SQLite 只保存索引、状态和关系 |
| Agent 运行时 | 现有 vha-codex-agent | 由宿主启动和监督独立 Codex 子进程，继续使用随机本机端口和私有运行目录 |
| 模型服务 | 用户配置的 OpenAI 兼容模型服务 | 仅用于 Agent 对话、规则生成、参数建议和问题分析，不内置模型服务 |
| 训练推理 | Python 3.11 + PyTorch 2.x CUDA + torchvision 0.x | 使用 Mask R-CNN 训练实例分割模型；具体版本随平台包锁定 |
| ML 进程协议 | stdin / stdout NDJSON | 避免额外本地端口，支持命令、进度、日志、结果和取消事件双向通信 |
| 图像处理 | Pillow / torchvision transforms | 服务于图片读取、增强、张量转换和结果可视化；不引入 Ultralytics 运行时依赖 |
| 测试 | cargo test、Svelte check、Node Test、Playwright、pytest | 单元、接口、前端交互、ML 逻辑和 GPU 集成测试分层执行 |
| 打包交付 | Cargo Release、Vite build、Python 独立运行环境 | Windows 在 bin/win/ 生成 zip；Linux 在 bin/linux/ 直接生成可运行绿色目录 |

### 1.4 设计原则

**宿主拥有生命周期**：Rust 宿主是唯一的应用入口，负责启动本地服务、Codex 子进程和 Python ML Worker。浏览器关闭只断开界面连接，不停止后台任务；托盘退出时按“停止新任务 → 请求任务取消 → 等待有限时间 → 强制回收进程树”的顺序清理，不遗留应用拥有的子进程。

**界面不接触敏感计算资源**：前端只通过本地 HTTP / WebSocket 调用后端，不直接读取数据库、模型文件、密钥或 GPU。模型密钥只保存在后端私有配置中，界面只接收脱敏信息。

**ML Worker 可替换**：训练和推理协议只交换任务 ID、数据集路径、参数、进度、指标和结果文件路径，不把 PyTorch 张量、CUDA 上下文或 Python 对象暴露给前端。后续更换训练框架时，不影响项目管理和标注协议。

**原图不可变**：导入图片写入项目原图目录后只读；标注、数据集版本、训练结果和推理结果均生成新文件或新记录。所有会覆盖重要数据的操作必须先成为用户确认过的阶段计划。

**任务可恢复可追溯**：长任务状态持久化到 SQLite，进度事件用于界面刷新。网页刷新或关闭后重新打开，可从数据库恢复任务状态；异常退出后下次启动标记待核对任务，不把未知状态伪装成成功。

**能力降级明确**：无 GPU 时项目、图片、标注和 Agent 对话继续可用，训练和推理明确提示不可承诺；模型服务不可用时本地项目功能继续可用，Agent 能力明确提示待修复。

**首版保持简单**：不做插件系统、公开数据集格式导出、Segment Anything 辅助预标注、多人协同、账号体系和云端同步。现有 source/backend/depends/ultralytics 只作为历史资料，不作为首版运行时依赖，避免 AGPL 许可与分发风险。

**跨平台优先验证**：Windows 和 Linux 使用同一业务协议和项目数据结构，平台差异集中在进程控制、GPU 运行时、托盘、浏览器启动和打包脚本。每个平台都必须实测启动、训练、推理、托盘退出和无残留进程。

### 2.2 运行时职责边界

| 运行单元 | 拥有的职责 | 不负责的事情 |
| --- | --- | --- |
| 浏览器前端 | 页面交互、标注可视化、任务状态展示、用户输入校验提示 | 不拥有进程、不直接访问数据库和文件系统、不执行训练 |
| Rust 宿主 | 本地 API、业务编排、SQLite事务、任务队列、子进程生命周期、配置、日志、托盘 | 不执行 PyTorch 训练和推理，不把 GPU 计算放进主进程 |
| Python ML Worker | GPU 检测、数据增强、Mask R-CNN 训练、评估、推理、结果文件生成 | 不直接写 SQLite，不管理项目生命周期，不与浏览器通信 |
| Codex 子进程 | Agent 会话、工具调用、审批、回合执行 | 不管理 Python Worker，不决定训练任务是否启动 |
| 外部模型服务 | Agent 使用的自然语言模型能力 | 不参与首版自动预标注和本地模型训练 |

### 2.4 任务生命周期

所有长任务遵循同一状态机：

~~~text
created → queued → running → succeeded
                          ├── failed
                          ├── cancelled
                          └── interrupted
~~~

| 状态 | 含义 | 恢复策略 |
| --- | --- | --- |
| created | 任务已创建，尚未排队 | 应用重启后可继续排队或由用户取消 |
| queued | 任务已入队，等待执行 | 应用重启后保留队列，按资源状态决定是否恢复 |
| running | Worker 正在执行 | 网页关闭不影响；宿主重启后先核对进程和产物 |
| succeeded | 任务成功且有结果文件 | 校验文件和指标记录后展示 |
| failed | 任务失败 | 保留错误、日志摘要和已完成产物 |
| cancelled | 用户确认取消 | 区分已完成、未处理和被中断部分 |
| interrupted | 宿主或 Worker 异常中断 | 下次启动标记待核对，不伪装成成功或失败 |

### 2.5 本地数据布局

~~~text
<应用目录>/
├── VisionHyperAgent                    # Linux 主程序；Windows 为 .exe
└── data/
    ├── vision.db                       # 全局 SQLite 元数据与状态库
    └── projects/<projectId>/
        ├── original/                   # 只读原图
        ├── annotations/                # 遮罩与标注版本
        ├── datasets/<datasetVersion>/  # 内部训练 manifest 与索引
        ├── models/<modelId>/           # 模型权重与配置
        ├── results/
        │   ├── training/<taskId>/      # 训练曲线、日志摘要、最优指标
        │   ├── evaluation/<evaluationId>/ # 指标、失败案例与可视化
        │   └── inference/<inferenceId>/   # 推理遮罩、类别、置信度与图片
        └── agent/                      # 项目相关规则、计划与执行记录文件
~~~

`vision.db` 是全局唯一 SQLite 数据库，通过 `projectId` 区分项目；这样项目列表、跨项目任务和启动恢复不需要扫描多个数据库。项目内大文件仍全部保存在对应项目目录，数据库只保存相对路径和元数据。

存储边界：

| 数据类型 | 存储位置 | 原因 |
| --- | --- | --- |
| 原图 | 项目目录 | 保持只读、可追溯、避免数据库膨胀 |
| 遮罩与标注文件 | 项目目录 | 大文件和版本化产物适合文件系统管理 |
| 数据集 manifest | 项目目录 | Worker 无需访问数据库即可复现训练输入 |
| 模型权重 | 项目目录 | 大文件独立保存，数据库只记录路径和状态 |
| 图片、标注、任务、指标记录 | SQLite | 支持查询、过滤、统计、事务和恢复 |
| API Key | 后端私有配置 | 不进入前端、日志、数据库快照和发布包 |

## 3. 模块职责划分

### 3.1 模块总览

首版采用 11 个核心模块。模块是逻辑边界，不要求每个模块都对应一个独立进程；后续源码目录和公开 API 文档按这些模块展开。

| 架构层 | 模块 | 核心职责 | 运行形态 |
| --- | --- | --- | --- |
| frontend | workspace-ui | 项目、图片、数据集、训练、评估、推理和设置页面 | 浏览器 |
| frontend | annotation-canvas | 实例遮罩绘制、编辑、缩放和平移 | 浏览器 |
| backend | api-gateway | HTTP / WebSocket 协议、静态资源、上传和错误映射 | Rust 宿主 |
| backend | project-service | 项目、图片、类别、标注、规则和数据集版本 | Rust 宿主 |
| backend | ml-service | 训练、评估、推理任务和模型候选管理 | Rust 宿主 |
| backend | agent-service | Agent 会话、规则建议、训练建议和执行计划记录 | Rust 宿主 |
| backend | task-runtime | 长任务状态机、事件、取消、恢复和进程监督 | Rust 宿主 |
| backend | storage | SQLite 迁移、仓储、项目文件和产物路径管理 | Rust 宿主 |
| backend | desktop-host | 启动、托盘、浏览器、退出清理和平台适配 | Rust 宿主 |
| backend | common-services | 日志、配置、错误、ID、时间、路径和敏感信息脱敏 | Rust 宿主 |
| ml-worker | mask-rcnn-worker | GPU 检测、数据加载、训练、评估、推理和结果文件生成 | Python 子进程 |

### 3.2 frontend / workspace-ui

**定位**：承载用户主流程，负责页面状态、表单、列表、图表和页面间导航；不实现业务规则，不直接访问后端私有数据。

| 子模块 | 职责 | 不负责 |
| --- | --- | --- |
| AppShell | 全局导航、页面布局、全局提示、任务状态入口 | 业务状态持久化 |
| ProjectWorkspace | 项目创建、项目切换、图片导入、状态筛选和批量确认 | 图片解码、数据库事务 |
| DatasetWorkspace | 数据集版本、类别分布、质量摘要和小样本风险展示 | 训练参数决策 |
| TrainingWorkspace | 训练计划确认、任务进度、日志摘要、指标曲线和停止操作 | GPU 调度 |
| EvaluationWorkspace | 整体指标、类别指标、失败案例和改进建议展示 | 指标计算 |
| InferenceWorkspace | 新图片选择、候选模型对比、遮罩结果和测试结论保存 | 模型加载 |
| SettingsWorkspace | 模型服务、Codex、数据目录和运行能力展示 | 明文展示或保存密钥 |
| AgentWorkspace | 对话、历史、附件、模型选择、Effort、审批和自然语言计划确认 | 直接执行训练或修改标注 |

页面状态来自后端快照和 WebSocket 事件。刷新页面时先恢复路由和会话，再向后端同步任务状态，不以本地 UI 状态作为最终事实。

### 3.3 frontend / annotation-canvas

**定位**：独立的高性能 2D 标注编辑模块，负责几何编辑和视觉呈现，不决定标注是否有效，也不直接落盘。

| 能力 | 设计要求 |
| --- | --- |
| 图层 | 原图层、已确认实例层、候选编辑层、当前绘制层和控制点层分离 |
| 工具 | 首版支持画笔、多边形、擦除、选择、移动、顶点编辑和删除 |
| 实例模型 | 每个实例包含实例 ID、类别 ID、遮罩或多边形、显示颜色和编辑状态 |
| 坐标 | 内部保存归一化坐标；渲染时映射到屏幕坐标，缩放平移不破坏精度 |
| 撤销重做 | 每张图片维护独立操作栈，至少支持 50 步 |
| 性能 | 4K 图片下使用区域重绘和 requestAnimationFrame 合并刷新，避免全画布频繁重绘 |
| 输出 | 只提交几何与实例变更，由后端校验类别、状态和版本后保存 |

Canvas 不直接调用数据库、Agent 或 ML Worker，也不把屏幕像素坐标当作最终存储坐标。

### 3.4 backend / api-gateway

**定位**：浏览器与 Rust 宿主之间的唯一协议边界，负责路由、参数校验、序列化、事件订阅和错误转换。

| 职责 | 说明 |
| --- | --- |
| HTTP API | 项目、图片、标注、数据集、任务、模型、设置和附件接口 |
| WebSocket | 任务进度、Agent 消息、状态修复和主动关闭通知 |
| 静态资源 | 服务前端构建产物和必要公开资源 |
| 上传 | 图片、测试图片和 Agent 附件的分块或 multipart 上传 |
| 错误映射 | 把内部错误转换为稳定错误码和用户可理解提示，不泄漏路径、密钥或堆栈 |
| 本地约束 | 默认只绑定本机地址，不提供公网访问 |

接口层不包含业务规则，不直接写 SQLite，不直接启动子进程；它只调用应用服务层。

### 3.5 backend / project-service

**定位**：管理视觉项目的核心业务数据，包括项目、图片、类别、标注、规则和数据集版本，保证事务一致性。

| 子模块 | 职责 |
| --- | --- |
| ProjectManager | 项目创建、打开、归档、删除前影响检查和项目索引 |
| ImageManager | 图片导入、格式校验、哈希去重提示、缩略图、状态管理和异常标记 |
| CategoryManager | 类别新增、改名、合并、停用和引用影响提示 |
| RuleManager | 标注规则版本、用户确认记录、冲突记录和与数据集版本的绑定 |
| AnnotationManager | 实例标注保存、逐图确认、撤销快照引用、无目标样本和异常数据管理 |
| DatasetManager | 从已确认标注生成不可变数据集版本、统计类别分布和导出训练 manifest |

数据集版本一旦生成，不原地修改。后续标注变化通过新版本表达；训练记录始终引用创建时的版本 ID。

### 3.6 backend / ml-service

**定位**：面向训练、评估、推理和模型候选的业务服务。它负责是否允许创建任务、任务参数和结果登记，不直接执行 GPU 计算。

| 子模块 | 职责 |
| --- | --- |
| TrainingRequestHandler | 校验数据集、模型、参数、GPU 状态和用户确认记录，创建训练任务 |
| EvaluationRequestHandler | 为指定模型和数据集创建评估任务 |
| InferenceRequestHandler | 为新图片或对比任务创建推理任务 |
| ModelCandidateManager | 管理模型 ID、权重路径、训练来源、指标、状态和当前候选选择 |
| MlEventCoordinator | 把 Worker 进度转换成任务事件和前端可理解状态 |
| ResourcePolicy | 控制同一时间只运行一个 GPU 训练任务，评估和推理按队列调度 |

模型权重和结果文件写入项目目录，数据库只登记相对路径、指标摘要和状态。Worker 崩溃时，任务进入 interrupted，不允许把半成品模型标记为可用。

### 3.7 backend / agent-service

**定位**：把 Codex 能力接入视觉业务，负责对话、项目上下文、规则建议、训练建议和阶段计划记录；不直接修改业务数据。

| 子模块 | 职责 |
| --- | --- |
| ConversationManager | Agent 会话、历史、附件、模型选择、Effort 和停止当前回合 |
| ProjectContextBuilder | 汇总项目目标、规则版本、类别、数据集统计和任务结果，形成上下文摘要 |
| RuleAdvisor | 生成或修订标注规则，并记录用户确认版本 |
| TrainingAdvisor | 根据数据集统计和历史训练结果生成参数建议与风险说明 |
| PlanRecorder | 记录阶段计划、参数、影响范围、确认状态和实际执行偏差 |
| ApprovalBridge | 处理 Codex 审批和追问，保证用户确认后才执行外部动作 |

Agent 的建议必须通过对应业务服务落库或触发任务。agent-service 不能绕过 project-service 直接写标注文件，也不能绕过 ml-service 直接启动训练。

### 3.8 backend / task-runtime

**定位**：统一管理长任务生命周期和子进程，不包含视觉业务规则。

| 能力 | 说明 |
| --- | --- |
| 状态机 | created、queued、running、succeeded、failed、cancelled、interrupted |
| 队列 | 按任务类型和资源策略排队，避免多个 GPU 任务同时抢占显存 |
| 事件总线 | 向 WebSocket 发布任务事件，并向 SQLite 写入关键状态变化 |
| 取消 | 先发送取消请求，超时后终止 Worker 进程，并记录实际完成范围 |
| 恢复 | 启动时核对运行中任务、进程和产物，把不可确认状态标记 interrupted |
| 进程监督 | 启动、重启、回收 ML Worker；AgentRuntime 继续负责 Codex 子进程 |

task-runtime 是并发和可恢复性的唯一权威。业务服务不能自行 spawn 训练进程，也不能直接把任务标为成功。

### 3.9 backend / storage

**定位**：封装 SQLite 和项目文件访问，向上提供仓储接口，防止业务服务散落 SQL 和路径规则。

| 子模块 | 职责 |
| --- | --- |
| DbMigrator | 管理数据库版本、迁移脚本和启动校验 |
| Repository | 项目、图片、标注、数据集、任务、模型、指标和 Agent 记录查询写入 |
| UnitOfWork | 标注确认、数据集生成等复合操作使用事务保证一致性 |
| FileStore | 管理原图、遮罩、数据集、模型、结果和 agent 文件的相对路径 |
| ThumbnailStore | 生成和缓存图片缩略图 |
| IntegrityChecker | 启动时核对数据库记录与磁盘产物，标记缺失或损坏记录 |

SQLite 使用 WAL 模式和 Rust 侧连接池，默认单进程写入。Python Worker 不获得数据库连接，只读写明确授权的任务目录和 manifest 文件。

### 3.10 backend / desktop-host

**定位**：负责桌面运行形态和跨平台宿主能力，不参与业务流程。

| 子模块 | 职责 |
| --- | --- |
| StartupSequence | 初始化日志、配置、数据库、HTTP 服务、托盘、Codex 和恢复检查 |
| TrayController | 托盘图标、打开界面、退出入口和状态提示 |
| BrowserLauncher | 启动或聚焦默认浏览器 |
| ShutdownCoordinator | 停止新任务、取消任务、回收 Codex 和 Worker、保存状态并退出 |
| PlatformAdapter | Windows / Linux 进程树、权限、路径和可执行行为差异 |

浏览器关闭只断开界面，不触发宿主退出。托盘退出是唯一正常退出入口，必须确保应用拥有的 Codex 和 ML Worker 不残留。

### 3.11 backend / common-services

**定位**：提供与业务无关的基础能力，保持无状态或全局单例，不依赖上层模块。

| 能力 | 设计要求 |
| --- | --- |
| 日志 | 按天输出、毫秒时间、级别、来源位置，不记录密钥、原图内容和用户消息正文 |
| 配置 | 原子读写、损坏备份、默认值、敏感字段脱敏 |
| 错误 | 统一错误分类、错误码、用户提示和内部诊断信息 |
| ID / 时间 | 生成稳定 ID 和统一时区、格式化规则 |
| 路径 | 解析应用目录、数据目录、项目相对路径，禁止路径穿越 |
| 脱敏 | API Key、授权头、私有路径和附件内容的统一过滤 |

### 3.12 ml-worker / mask-rcnn-worker

**定位**：唯一执行 PyTorch GPU 计算的 Python 子进程，负责训练、评估、推理和结果文件生成，不参与项目管理和界面状态。

| 子模块 | 职责 |
| --- | --- |
| WorkerProtocol | 解析 stdin NDJSON 命令，向 stdout 输出进度、日志、结果和错误 |
| EnvironmentProbe | 检测 Python、PyTorch、CUDA、设备名称和显存容量 |
| DatasetLoader | 读取训练 manifest、图片和遮罩，执行数据集划分与增强 |
| MaskRcnnTrainer | 训练 torchvision Mask R-CNN，输出 checkpoint、最终权重和训练曲线 |
| EvaluationEngine | 计算 mask mAP、IoU、类别指标和失败案例 |
| InferenceEngine | 加载候选模型，输出实例遮罩、类别、置信度和可视化图片 |
| ResultWriter | 按任务目录写结果 JSON、图片和指标文件 |

Worker 只能访问任务指令中明确给出的项目子目录。任何 SQLite 更新都由 Rust 宿主根据 Worker 完成事件执行。

### 3.13 模块依赖规则

~~~text
workspace-ui ─────────── api-gateway ─────────────── project-service
    │                          │                          │
annotation-canvas              ├── ml-service ─────────── storage
                               ├── agent-service          │
AgentWorkspace ────────────────┤                          │
                               ├── task-runtime ──────────┤
                               └── desktop-host           │
                                                          │
task-runtime ───────────── mask-rcnn-worker               │
~~~

| 调用关系 | 允许 | 禁止 |
| --- | --- | --- |
| workspace-ui → api-gateway | 调用 HTTP / WebSocket | 直接调用 Rust 服务和仓储 |
| project-service → storage | 事务读写项目数据 | 直接启动 Worker、访问模型服务 |
| ml-service → task-runtime | 创建和管理 ML 任务 | 自行 spawn Python 进程 |
| agent-service → project/ml-service | 读取上下文、提交建议结果 | 绕过业务服务写库或改文件 |
| task-runtime → ml-worker | 启动、取消、回收 Worker | 理解训练参数和模型指标 |
| ml-worker → 文件目录 | 读取 manifest、写任务结果 | 连接 SQLite、访问浏览器和 Agent |
| desktop-host → 各服务 | 按启动顺序组装和关闭 | 实现业务规则 |
| common-services → 无 | 提供基础能力 | 依赖业务模块 |

### 3.14 关键职责切分

| 问题 | 归属模块 | 说明 |
| --- | --- | --- |
| 图片是否有效 | project-service | 负责导入校验和状态登记 |
| 遮罩几何是否正确 | annotation-canvas + project-service | Canvas 负责编辑，后端负责版本和引用校验 |
| 数据集能否生成 | project-service | 检查确认状态、类别、规则和图片范围 |
| 训练参数是否合理 | agent-service + ml-service | Agent 给建议，ml-service 校验硬约束 |
| 何时启动 GPU 任务 | task-runtime | 统一排队和资源控制 |
| 模型效果如何 | mask-rcnn-worker | 训练与指标计算 |
| 哪个模型是候选 | ml-service | 根据指标、测试记录和用户选择登记 |
| 任务是否成功 | task-runtime | 必须核对完成事件和产物 |
| 数据是否丢失 | storage | 事务和完整性检查 |
| 进程是否退出 | desktop-host | 托盘退出和进程树回收 |

## 4. 三方库集成策略

| Tokio 1 | backend 全局 | 异步运行时、任务调度和进程管理 | 锁定兼容版本 |

| Python 3.11 | mask-rcnn-worker | ML Worker 运行语言 | Windows / Linux 分别锁定同一小版本 |
| PyTorch 2.x CUDA | mask-rcnn-worker | GPU 训练与推理 | 按平台锁定具体 wheel 版本 |
| torchvision 0.x | mask-rcnn-worker | Mask R-CNN、数据变换和检测算子 | 与 PyTorch 版本严格配对 |
| Pillow | mask-rcnn-worker | 图片读取和结果可视化 | 锁定安全版本 |
| NumPy | mask-rcnn-worker | 数组转换与遮罩处理 | 与 PyTorch 版本兼容 |
| torchmetrics | mask-rcnn-worker | 分割指标计算 | 只在 Worker 内使用，不进入 Rust 接口 |
| pytest | ml-worker 测试 | ML 逻辑和协议测试 | 开发依赖，不进入发布包 |

不引入 Ultralytics 作为首版运行时依赖；`source/backend/depends/ultralytics` 仅保留为历史资料，不参与构建和发布。

### 4.2 前端依赖集成

#### Svelte / Vite / TypeScript

| 项目 | 约束 |
| --- | --- |
| 集成位置 | source/frontend |
| 构建产物 | dist/，由 Rust 宿主嵌入或随绿色包分发 |
| 开发代理 | /api 与 /ws 转发到本地 Rust 服务 |
| 类型边界 | API 请求、响应、WebSocket 事件必须有 TypeScript 类型 |
| 状态边界 | 组件只保存 UI 状态，业务事实以后端快照为准 |
| 升级策略 | 先通过 svelte-check、单元测试和 Playwright，再升级锁文件 |

前端不得为了局部功能直接引入大型 UI 库或状态管理库。首版优先使用 Svelte 组件、浏览器原生能力和少量手写公共组件，避免包体和风格失控。

#### Playwright

Playwright 只用于自动化验收，不进入发布包。E2E 用例必须覆盖：

1. 项目创建与图片导入。
2. 标注编辑与逐图确认。
3. 数据集生成入口状态。
4. 训练任务确认、进度展示和取消。
5. 推理结果展示。
6. 页面刷新后的状态恢复。

### 4.3 Rust 依赖集成

#### axum / Tokio

| 项目 | 约束 |
| --- | --- |
| 集成位置 | vha-server 与 task-runtime |
| 服务地址 | 默认 127.0.0.1，不提供公网监听 |
| WebSocket | 单连接多事件订阅，不用轮询模拟实时状态 |
| 生命周期 | Tokio 任务必须可取消，退出时使用有限超时等待 |
| 测试 | 使用 axum test utilities 和模拟服务测接口 |

axum handler 不直接访问数据库或子进程，只做参数解析、权限与本地来源检查、服务调用和错误映射。

#### SQLx / SQLite

| 项目 | 约束 |
| --- | --- |
| 集成位置 | storage 模块 |
| 数据库文件 | data/vision.db |
| SQLite 来源 | SQLx bundled SQLite，避免依赖用户系统库 |
| 模式管理 | SQLx migrations，启动时检查并迁移 |
| 查询方式 | 运行时 SQL 与仓储封装，业务层不拼接 SQL |
| 并发模式 | WAL；写操作集中在 Rust 宿主进程 |
| 备份策略 | 应用空闲或退出前可执行 SQLite backup；训练大文件不进数据库 |

SQLx 连接池只由 storage 模块创建和持有。业务服务通过仓储接口访问，不把数据库类型暴露到 API 层或 Python Worker。

#### image

image 用于图片格式校验、尺寸读取和缩略图生成。原图校验通过后复制到项目 original/ 目录；后续标注、训练和推理均不再修改原图文件。

支持的输入格式首版锁定为 JPEG、PNG 和 WebP。其他格式先提示不可导入，不做动态格式扩展。

#### tray-icon / tao / webbrowser

| 能力 | Windows 策略 | Linux 策略 |
| --- | --- | --- |
| 托盘 | 使用系统通知区图标和右键菜单 | 兼容主流桌面环境；无托盘环境提供 headless 退化说明 |
| 浏览器 | 打开默认浏览器本地地址 | 打开默认浏览器或 xdg-open 本地地址 |
| 事件循环 | 由 tao 处理托盘事件 | 保持与 Linux 桌面事件循环兼容 |
| 验证 | 实机验证图标、打开界面、退出清理 | 实机验证图标、打开界面、退出清理 |

桌面依赖不进入业务层。业务服务不得感知托盘、浏览器或窗口事件。

### 4.4 Python ML 依赖集成

#### PyTorch / torchvision

| 项目 | 约束 |
| --- | --- |
| 集成位置 | source/ml-worker 独立目录 |
| 设备策略 | 只在 Worker 内创建 CUDA 上下文 |
| 版本配对 | torchvision 版本必须与 PyTorch 官方兼容表一致 |
| CUDA 运行库 | 随 PyTorch wheel 打入平台包 |
| GPU 驱动 | 不打包 NVIDIA 驱动，由用户系统提供 |
| 自动设备选择 | Worker 启动时检测 CUDA、GPU、驱动能力和显存；环境满足时自动使用 GPU |
| 无 CUDA 策略 | 不静默降级为 CPU 训练或推理，基础项目功能继续可用并提示缺少 NVIDIA 官方驱动 |
| 显存策略 | 训练任务串行；推理和评估按任务队列执行 |
| 失败隔离 | Worker 崩溃只影响当前 ML 任务，不拖垮 Rust 宿主 |

首版模型使用 torchvision Mask R-CNN。允许后续增加模型家族，但模型实现必须留在 Python Worker 内，不能把 PyTorch 类型泄漏到 Rust 或前端协议。

#### Pillow / NumPy / torchmetrics

| 依赖 | 边界 |
| --- | --- |
| Pillow | 只在 Worker 内读图、写可视化图片 |
| NumPy | 只在 Worker 内处理数组与遮罩 |
| torchmetrics | 只负责指标计算，输出 JSON 可序列化结果 |

Python 依赖必须由锁文件复现，不在用户机器上执行 pip install。发布包内置 Python 运行时和依赖目录。

### 4.5 模型服务与 Codex 集成

| 项目 | 约束 |
| --- | --- |
| 配置来源 | 用户在设置页配置，后端私有保存 |
| 密钥边界 | 不进入前端明文响应、日志、SQLite 明文快照和发布包 |
| 用途边界 | 只用于 Agent 对话、规则生成、训练建议和问题分析 |
| 进程边界 | Codex 由 AgentRuntime 启动和监督，使用随机本机端口 |
| 业务边界 | Agent 不得直接写项目数据或启动训练 |
| 失败边界 | 模型服务不可用不影响项目、图片和标注功能 |

Codex 和模型服务相关类型只停留在 agent-service 与 codex_agent 模块；视觉业务模块不依赖模型服务协议。

### 4.6 依赖锁定与构建复现

| 生态 | 锁定文件 | 说明 |
| --- | --- | --- |
| 前端 | package-lock.json | 锁定 npm 依赖和脚本入口 |
| Rust | Cargo.lock | 锁定全部 crate 版本 |
| Python | requirements.lock 与平台 wheel 清单 | 锁定 Python 包和 PyTorch / torchvision 配对版本 |
| 构建脚本 | build.sh 与平台配置 | 不依赖开发者本机临时安装的包 |

构建机必须能复现出相同产物。CI 或本地发布时记录：

1. 前端、Rust、Python 锁文件哈希。
2. PyTorch / torchvision / CUDA wheel 版本。
3. 目标操作系统与架构。
4. 产物大小和 SHA256。

### 4.7 绿色包集成

| 平台 | 交付形态 | 运行时策略 |
| --- | --- | --- |
| Windows | bin/win/VisionHyperAgent-windows-x64.zip | zip 内包含主程序、Codex 副本、前端产物、Python 运行时和 CUDA 依赖 |
| Linux | bin/linux/ 绿色目录 | 目录内包含主程序、Codex 副本、前端产物、Python 运行时和 CUDA 依赖 |

绿色包约束：

- 不要求用户安装 Rust、Node.js、Python 或 pip。
- 不要求用户编译任何组件。
- 不在首次启动时下载 PyTorch、torchvision 或前端资源。
- NVIDIA GPU 驱动仍由用户系统提供。
- Windows / Linux 主机已安装满足内置 CUDA 运行库要求的 NVIDIA 官方驱动时，应用解压后可直接自动使用 GPU。
- 未安装驱动、驱动版本过旧或 Linux 使用 nouveau 时，应用不自动安装或修改驱动，只报告具体原因和修复建议。
- Python Worker、Codex 和主程序的路径由 Rust 宿主解析。
- 删除应用目录即删除应用本体；用户项目数据若迁移到外部目录，需在设置中明确显示。

### 4.8 第三方库归属一览

| 库 / 运行时 | 归属层 | 允许依赖 | 禁止依赖 |
| --- | --- | --- | --- |
| Svelte / Vite | frontend | TypeScript、浏览器 API | Rust 类型、SQLite、文件系统 |
| Canvas 2D | annotation-canvas | 浏览器 API | Three.js、后端私有类型 |
| axum / Tokio | backend | storage、service、runtime | 业务 SQL、PyTorch |
| SQLx / SQLite | storage | 迁移、仓储接口 | 前端、Python Worker 直接连接 |
| image | project-service | 图片格式、缩略图 | 模型推理 |
| tray-icon / tao / webbrowser | desktop-host | 平台 API | 业务服务 |
| reqwest | agent-service | 用户模型服务 | 视觉训练与推理 |
| PyTorch / torchvision | ml-worker | CUDA、数据集目录 | SQLite、浏览器、Codex |
| Pillow / NumPy / torchmetrics | ml-worker | Worker 内数据处理与指标 | 公共协议类型泄漏 |
| Playwright / pytest | 测试环境 | 被测接口与页面 | 发布包 |

### 4.9 依赖风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| PyTorch CUDA 包体积大 | 绿色包明显变大 | Windows / Linux 分包；只打包目标平台必需 wheel |
| CUDA 与驱动不匹配 | 训练或推理失败 | Worker 启动时报告驱动、CUDA 和显存能力；锁定 wheel 版本后在文档中写明最低 NVIDIA 驱动版本 |
| 缺少 NVIDIA 官方驱动 | GPU 任务无法自动运行 | 不自动安装驱动；明确提示 Windows / Linux 安装官方驱动，Linux 不支持仅 nouveau 的 CUDA 场景 |
| Linux 桌面环境差异 | 托盘不可用或行为不一致 | 支持主流发行版实测；无托盘时给出可理解降级 |
| torchvision 与 PyTorch 版本错配 | 模型加载或算子失败 | 锁定官方配对版本并做导入冒烟测试 |
| SQL 模式演进失败 | 应用无法启动 | 迁移前检测数据库版本；迁移失败保留原库并给出恢复说明 |
| 前端依赖膨胀 | 包体变大、风格不一致 | 首版不引入大型 UI 库；新增依赖需说明不可替代性 |
| 在线模型服务不可用 | Agent 建议不可用 | 本地项目功能继续可用，并给出配置修复提示 |

## 5. 场景与数据流

### 5.1 应用启动与恢复

~~~text
用户启动主程序
    │
    ▼
desktop-host 初始化应用目录、日志和配置
    │
    ▼
storage 打开 data/vision.db 并执行迁移
    │
    ▼
IntegrityChecker 核对数据库记录与磁盘产物
    ├── 缺失标注或模型文件 → 标记记录可疑
    ├── 上次 running 任务 → 按完成凭证核对后恢复或标记 interrupted
    └── queued / created 任务 → 保留并等待用户处理
    │
    ▼
api-gateway 启动本机 HTTP / WebSocket 服务
    │
    ▼
desktop-host 创建托盘并打开浏览器
    │
    ▼
AgentRuntime 启动并监督 Codex 子进程
    │
    ▼
前端加载项目列表、任务状态和 Agent 状态
~~~

启动约束：

- Python ML Worker 不随主程序常驻启动，只在环境检测、训练、评估或推理时按需启动。
- 数据库迁移失败时保留原库，不删除用户数据，界面显示恢复指引。
- Codex 启动失败不阻塞项目、图片和标注功能，只降低 Agent 能力。
- 上次异常退出的任务不能仅凭数据库 running 状态判断为成功或失败。

~~~text
用户创建项目

    ▼
~~~

图片导入流程：

~~~text
用户选择一张或多张图片
    │
    ▼

    │
    ▼
project-service 检查格式、尺寸和可解码性
    ├── 无效文件 → 删除临时文件并返回具体原因
    └── 有效文件 → 计算内容哈希
    │
    ▼
同一项目内发现相同哈希
    ├── 用户选择跳过 → 保留原记录
    └── 用户选择重复导入 → 生成独立图片记录并标记重复
    │
    ▼

    │
    ▼
生成缩略图并写入 SQLite 图片记录
    │
    ▼
WebSocket 推送导入进度和最终统计
~~~

导入规则：

| 项目 | 规则 |
| --- | --- |
| 支持格式 | JPEG、PNG、WebP |
| 原图修改 | 禁止；导入后只读 |
| 失败处理 | 单张失败不中断整批导入 |
| 重复判断 | 以项目为范围计算内容哈希 |

### 5.3 Agent 规则生成与确认

~~~text
用户描述要识别的目标
    │
    ▼
agent-service 构建项目上下文摘要
    ├── 已有规则版本
    ├── 类别定义
    ├── 图片统计
    └── 已确认数据情况
    │
    ▼
Codex 结合用户描述生成规则草案或追问
    ├── 信息不足 → Agent 继续提问
    └── 信息足够 → 输出类别、边界、排除条件和易混淆说明

    ▼

    │
    ▼
用户明确确认规则
    │
    ▼
project-service 创建新的规则版本并记录确认依据
    │
    ▼
前端刷新当前有效规则
~~~

边界规则：

- Agent 可以建议规则，不能直接写规则生效版本。
- 规则生效必须来自用户明确确认。
- 冲突规则由 Agent 指出并由用户选择。
- 后续数据集版本必须记录创建时使用的规则版本。

标注数据包含：

manifest 内容：

### 5.6 GPU 环境检测

~~~text

    │
    ▼
ml-service 请求环境能力
    │
    ▼
task-runtime 按需启动 Python Worker
    │
    ▼
EnvironmentProbe 输出环境报告
    ├── Python / PyTorch / torchvision 版本
~~~

环境报告写入 SQLite，并作为任务可复现性的一部分保存。应用不自动安装或修改 NVIDIA 驱动。

训练命令输入：

| 数据 | 说明 |

### 5.10 任务取消、网页关闭与异常恢复

#### 用户取消任务

~~~text
用户点击停止或自然语言请求停止
    │
    ▼
api-gateway 调用 task-runtime 取消任务
    │
    ▼
任务状态改为 cancelling
    │
    ▼
task-runtime 向 Worker 发送 cancel 命令
    │
    ▼
Worker 停止后续 epoch / 图片处理并输出取消凭证
    ├── 有限时间内完成 → cancelled
    └── 超时 → 终止进程树并标记 cancelled_after_timeout
    │
    ▼
storage 记录已完成数量、未处理数量和保留产物
~~~

#### 网页关闭或刷新

- 后端任务继续运行。
- WebSocket 断开不触发任务取消。
- 前端重新打开后按 taskId 恢复进度。
- 丢失的事件通过任务快照补齐。

#### Worker 崩溃

~~~text
Worker 进程异常退出
    │
    ▼
task-runtime 捕获退出码和 stderr 摘要
    │
    ▼
检查 completion.json 和产物哈希
    ├── 完整有效 → 允许登记成功
    └── 缺失或不一致 → 任务标记 interrupted
    │
    ▼
保留可用 checkpoint 和诊断信息
~~~

#### 主程序异常退出

下次启动时：

1. 查找 running / cancelling 任务。
2. 检查是否存在可信完成凭证。
3. 能验证的登记结果。
4. 不能验证的标记 interrupted。
5. 提示用户重试、继续或废弃任务。

### 5.11 应用退出清理

~~~text
用户从托盘选择退出
    │
    ▼
desktop-host 停止接收新任务
    │
    ▼
task-runtime 向运行中 ML 任务发送取消
    │
    ▼
等待 Worker 保存状态并退出
    ├── 正常退出 → 登记取消结果
    └── 超时 → 平台进程树强制回收
    │
    ▼
AgentRuntime 停止 Codex 子进程
    │
    ▼
HTTP / WebSocket 服务优雅关闭
    │
    ▼
storage 完成状态写入并释放连接池
    │
    ▼
移除托盘图标并退出主进程
~~~

退出验收必须确认：

- 无 VisionHyperAgentCodex 子进程残留。
- 无 ML Worker 子进程残留。
- 数据库中没有虚假的 succeeded 状态。
- 保留的取消和中断任务可以在下次启动解释。

### 5.12 数据一致性与事件流

一致性规则：

| 场景 | 处理方式 |
| --- | --- |
| 复合业务写入 | 使用 SQLite 事务 |
| 文件写入 | 临时文件 + 原子重命名 |
| 数据集生成 | 数据库记录与 manifest 同步提交，失败则整体不可见 |
| Worker 产物 | 以完成凭证和哈希为准，不以进程退出码为准 |
| 路径访问 | Worker 只能访问任务指定目录，禁止路径穿越 |
| 原图 | 只读，不参与覆盖写 |
| 确认版本 | 不可变，新修改生成新版本 |

WebSocket 任务事件按阶段推送：

~~~text
task.created
task.queued
task.running
task.progress
task.metric
task.log
task.cancel-requested
task.cancelled
task.succeeded
task.failed
task.interrupted
~~~

事件只携带任务状态和摘要，不携带大尺寸图片、模型权重或敏感配置。前端需要完整内容时，通过对应资源接口按需获取。

## 6. 异常处理与安全边界

> 本章为已定稿方案。所有异常都必须有稳定状态、用户可理解提示、内部诊断信息和可恢复策略；不以静默降级代替错误处理。

### 6.1 异常分类

| 类别 | 示例 | 用户表现 | 系统处理 |
| --- | --- | --- | --- |
| 输入异常 | 图片格式不支持、遮罩几何非法、参数超范围 | 指出具体对象和修复建议 | 拒绝本次操作，不改变已有确认版本 |
| 配置异常 | 模型服务地址无效、密钥缺失、Python 运行时损坏 | 设置页显示可修复原因 | 保留旧配置，校验通过后才替换 |
| 资源异常 | GPU 不可用、显存不足、磁盘空间不足 | 显示资源状态和影响范围 | 不启动不满足条件的任务，保留项目数据 |
| 外部服务异常 | Codex 断开、模型服务超时、限流 | Agent 区域显示暂不可用 | 保存本地草稿和会话，允许重连或稍后重试 |
| Worker 异常 | Python 进程崩溃、模型加载失败、结果文件缺失 | 任务显示失败或中断 | 校验完成凭证和产物，保留诊断信息 |
| 存储异常 | SQLite 锁定、迁移失败、文件写入失败 | 说明数据未提交或待恢复 | 事务回滚，原子文件写入保留旧版本 |
| 平台异常 | 托盘不可用、浏览器启动失败、进程回收超时 | 提供替代入口或退出提示 | 主服务可退化运行，退出时强制回收 |
| 并发异常 | 重复提交、版本冲突、重复取消 | 提示当前状态已变化 | 以数据库状态为准，幂等返回当前结果 |

### 6.2 错误处理链路

~~~text
底层异常
    │
    ▼
模块错误类型（包含内部原因和上下文）
    │
    ▼
应用服务错误码（稳定、可测试、可统计）
    │
    ▼
api-gateway 错误响应 / WebSocket error 事件
    │
    ├── 用户消息：简短、可理解、含下一步建议
    └── 内部日志：含模块、任务 ID、来源位置和诊断上下文
~~~

错误响应统一包含：

| 字段 | 说明 |
| --- | --- |
| code | 稳定错误码，如 image_invalid、gpu_unavailable、task_interrupted |
| message | 面向用户的中文提示 |
| retryable | 是否允许直接重试 |
| details | 经脱敏后的字段级错误详情 |
| correlationId | 用于关联日志和任务记录 |

禁止把 Rust panic、Python traceback、绝对路径、API Key 或完整请求内容直接返回浏览器。

### 6.3 数据与文件安全

| 边界 | 规则 |
| --- | --- |
| 原图 | 导入后只读，业务模块不能覆盖 |
| 标注版本 | 草稿可修改，确认版本不可变 |
| 数据集 | manifest 与数据库记录使用事务和哈希绑定 |
| 模型文件 | 仅由 ML Worker 写入任务专属目录，登记完成凭证后才进入候选列表 |
| 临时文件 | 写入应用临时目录，成功后原子移动，失败后清理 |
| 路径 | 所有用户路径解析后必须位于允许根目录，拒绝 .. 穿越和符号链接逃逸 |
| 导出 / 删除 | 需要用户明确操作，先显示影响范围；不静默删除历史版本 |
| 备份 | SQLite 备份和项目复制不包含运行日志、缓存和密钥 |

### 6.4 凭据与隐私

- API Key 只保存在后端私有配置，不返回前端明文。
- 日志过滤授权头、API Key、Cookie、附件内容和用户消息正文。
- Agent 上下文只发送完成当前任务所需的最小摘要，不默认上传原图或模型权重。
- 项目路径、数据库内容和模型文件不通过公网接口暴露；宿主默认只监听本机地址。
- 任何需要外部模型服务的调用都显示服务状态，不把外部服务响应伪装成本地训练结果。
- 发布前扫描源码、配置、日志、测试证据和压缩包，确认没有真实密钥。

### 6.5 进程与资源安全

| 项目 | 规则 |
| --- | --- |
| Codex 子进程 | 由 AgentRuntime 创建，使用独立 HOME、工作目录和随机端口；只回收本进程拥有的实例 |
| ML Worker | 由 task-runtime 创建，使用任务目录、受控环境变量和 stdin/stdout NDJSON；不继承无关密钥 |
| 进程树 | Windows 使用 Job Object 等价机制，Linux 使用进程组，退出时回收整个子树 |
| 资源限制 | 训练任务串行；任务有超时、取消和磁盘空间检查 |
| GPU 失败 | 不自动改用未经确认的 CPU 方案，不把资源失败归因于模型质量 |
| Worker 输入 | 只接受 Rust 生成的结构化命令，不执行用户拼接的 shell 命令 |

### 6.6 异常恢复与可观测性

启动恢复流程：

1. 读取数据库中 running、cancelling 和 queued 任务。
2. 检查应用拥有的进程是否仍存在。
3. 检查完成凭证、产物清单和哈希。
4. 能够证明完成的任务登记为成功。
5. 无法证明的任务登记为 interrupted，并保留重试、恢复或废弃入口。

可观测性要求：

| 记录 | 必须包含 | 禁止包含 |
| --- | --- | --- |
| 应用日志 | 时间、级别、模块、行号、任务 ID、错误码 | 密钥、完整用户消息、原图内容 |
| 任务记录 | 输入版本、参数摘要、状态变化、耗时、结果路径 | 未脱敏外部响应 |
| Worker 日志 | 设备、版本、阶段、指标、退出码 | API Key、无关环境变量 |
| 审计记录 | Agent 计划、用户确认、实际执行和偏差 | 未经用户同意的隐式操作 |

### 6.7 安全与异常验收

| 验收场景 | 通过标准 |
| --- | --- |
| 输入非法图片 | 单张失败可解释，其他图片继续处理，原图和已有标注不受影响 |
| 路径穿越 | 请求被拒绝，数据库和文件目录不产生越权文件 |
| 模型服务不可用 | 项目和标注仍可使用，Agent 区域显示可修复提示 |
| GPU / 驱动缺失 | 不启动训练或推理，明确说明原因 |
| Worker 崩溃 | 任务不伪装成功，保留退出码、日志和可用中间产物 |
| 主程序异常退出 | 重启后能区分成功、失败和中断任务 |
| 网页关闭 | 后台任务继续，重新进入后状态可同步 |
| 托盘退出 | Codex、ML Worker 和进程树全部回收 |
| 日志泄密扫描 | 日志、配置、数据库快照和发布包无真实密钥 |

## 7. 开发计划

> 本章为已定稿开发基线，开发顺序遵循模块依赖。每个模块完成后必须同时交付源码、测试、API 文档更新和可运行验证，不允许只完成代码而跳过测试或文档。

### 7.1 开发顺序总览

~~~text
第一批：公共基础与宿主骨架
  common-services → storage → task-runtime → desktop-host → api-gateway

第二批：项目与 Agent 业务
  project-service → agent-service → ml-service
          │               │             │
第三批：前端工作区与标注
  workspace-ui ↔ annotation-canvas
                  │
第四批：Python ML Worker 与闭环集成
  mask-rcnn-worker → 训练 / 评估 / 推理联调

  性能、异常恢复、GPU、Windows / Linux 打包和发布验收
~~~

| --- | --- | --- | --- |
