# 团队编码规范

| 项目 | 内容 |
| --- | --- |
| 版本 | 0.1 |
| 日期 | 2026-09-07 |
| 适用范围 | VisionHyperAgent 的 Rust、Slint、Python 代码及相关文档 |
| 当前状态 | Rust 工程骨架已建立；业务模块、Python 训练环境和 CI 尚未接入 |

本规范约束当前及后续获准开展的代码工作。当前授权仅为工程骨架初始化，不自动扩大到业务实现、运行环境安装或实施计划。产品范围以 [产品需求文档](产品需求文档.md) 为准，仓库协作入口为 [AGENTS.md](../AGENTS.md)。

“必须”“禁止”表示团队基线；“建议”表示允许在说明理由后调整的实践。规范例外应限定范围、说明原因和风险，不得通过例外静默改变产品需求。

## 1. 通用原则

- 优先可读性、正确性和可验证性，再进行有依据的性能优化。
- 每个模块承担清晰职责，通过明确接口协作，不为尚未确认的需求提前建设框架。
- 保持变更聚焦，不把新功能、全仓库格式化、依赖升级和无关重构混入同一修改。
- 遵循已选方案 A：Python 训练、Rust 推理；一个软件内部的职责分离不等于拆分产品。
- 团队说明、产品文档和面向用户的文案默认使用中文；代码标识符使用清晰的英文名称。
- 注释解释原因、约束和边界，不重复代码表面含义。公共接口应说明输入、输出、错误和副作用。
- 不凭经验填入未确认的操作系统版本、GPU 型号、训练指标、预算、协议或性能阈值。

## 2. 模块职责与依赖方向

以下是职责规范，不表示对应业务功能已经实现。当前目录与骨架状态以软件框架文档为准。

| 职责 | 要求 |
| --- | --- |
| Slint 界面 | 负责呈现和交互，通过明确接口调用业务逻辑，不直接执行训练、推理或外部通信。 |
| Rust 业务控制 | 管理任务状态、数据流和组件协作；不把业务规则分散到界面回调与协议解析中。 |
| Agent 适配 | 对接 Codex CLI 与官方 YOLO 技能，隔离上游接口变化，不自建替代 Agent 引擎。 |
| Python 训练执行 | 负责 YOLO26 训练、调参、评估和导出，不承接生产推理、相机或主界面职责。 |
| Rust 推理 | 处理模型加载和实例分割推理，不能依赖在线 Agent 或 Python 训练进程。 |
| 图像与通信接入 | OpenCV 与 ZeroMQ 适配外部输入，复用推理能力，不各自复制一套业务逻辑。 |
| runtime 管理 | 统一定位和管理私有运行资源，避免调用方散落硬编码环境路径。 |

模型、协议或外部进程的变化应尽量局限于对应适配部分。不得为了未来扩展而提前实现多协议插件系统。

## 3. Rust 编码规范

### 3.1 格式与命名

- 使用 rustfmt 统一格式，不手工维护与格式化器冲突的排版。
- 模块、函数、方法和变量使用 `snake_case`；类型与 trait 使用 `UpperCamelCase`；常量与静态项使用 `SCREAMING_SNAKE_CASE`。
- 名称表达业务含义，避免无意义缩写，以及长期堆积职责的 `utils`、`common` 模块。
- 默认最小可见性，需要跨模块使用时再开放接口；不为方便调用而无差别公开内部状态。
- 当前 Rust 骨架使用 2024 edition；本机验证工具链见 README。最低支持版本与最终工具链策略仍待后续依赖基线确认，不把开发机版本当作全部平台的兼容承诺。

### 3.2 类型与错误

- 使用明确类型表达任务、模型和运行状态，避免依赖散落的魔法字符串或布尔组合。
- 可预期的文件、网络、相机、GPU、模型和子进程失败必须通过 `Result` 等可处理路径返回。
- 禁止在生产外部输入路径使用 `unwrap()`、`expect()` 或 `panic!()` 代替错误处理。
- 测试中的断言，以及已证明的内部不变量可有限例外；必须能解释不变量为何成立。
- 在层级边界补充错误上下文，保留底层原因；不能以空结果或默认成功值掩盖失败。
- 枚举等封闭状态应尽量完整匹配，避免通配分支隐藏新状态未被处理的问题。

### 3.3 所有权、并发与 FFI

- 优先清晰的所有权和借用关系，不为绕开设计问题大量复制图像、掩码或模型资源。
- 不在持有共享锁时执行不受控阻塞操作；队列、重试和后台任务须有明确的容量或结束机制。
- 新增 `unsafe` 必须说明必要性，将范围压到最小，并用 `SAFETY` 注释记录调用方和实现方承担的不变量。
- FFI 包装应说明资源所有权、释放方式和线程约束，不让裸句柄泄漏到无关业务模块。
- 不默认所有第三方类型都可跨线程共享，按所选版本的接口约束设计。

## 4. Python 训练代码规范

- 遵循 PEP 8 的可读性与命名习惯；公共函数和跨组件数据边界必须有类型注解。
- 训练逻辑应拆分为可理解、可测试的职责，不在单个脚本堆叠导入、配置、训练、评估和导出全部细节。
- 模块导入不得隐式启动训练、联网下载模型或执行大规模 GPU 初始化。
- 禁止空的异常处理和吞掉异常的 `except`；顶层异常处理应保留原因并返回明确失败状态。
- 从 Rust 接收参数、发出进度、返回错误及交付产物，应使用约定的结构化契约；不要让 Rust 解析面向人的自然语言日志来判断任务是否成功。
- 解释器和运行环境由软件选择，不依赖用户激活 Conda、系统 Python 或开发者机器上的绝对路径。
- 正式工程建立时统一选择并锁定格式化、lint、类型检查和测试工具；本轮不新增工具依赖或配置文件。

## 5. Slint 界面规范

- 界面组件负责显示状态和发出用户操作，不直接维护训练算法、推理逻辑或通信协议。
- 禁止在界面事件线程进行阻塞训练、推理、相机采集、网络等待或大文件处理。
- 后台结果通过所选 Slint 版本支持的事件循环机制更新界面，不从任意工作线程直接修改组件状态。
- 长任务的状态、错误和可用操作必须来自明确业务状态，不能只用零散控件属性推断任务生命周期。
- 重复的视觉样式和交互组件应集中复用；不要将布局与业务参数耦合。
- 用户文案表达可采取的操作，不直接把堆栈、原始协议内容或未经处理的异常作为正常界面提示。
- 具体页面、控件、快捷键与交互流程须另行设计，本规范不替代 UI 设计确认。

## 6. 跨进程、图像与接口契约

- 对跨进程或外部输入进行结构、类型、范围和资源限制检查；Agent 生成的初标同样需要校验，不能视为天然可信数据。
- 先明确消息契约，再实现通信。ZeroMQ 模式、消息编码和字段尚未确认，不在规范中指定默认协议。
- 实例分割接口必须说明图像尺寸、坐标空间、区域表达及类别映射；不得用矩形框假装提供分割结果。
- 裁剪、缩放、方向处理和后处理发生变化时，应同步检查标注、训练导出和 Rust 推理的映射关系。
- 业务结果、执行错误和日志应有清晰边界，不能用成功响应包裹实际失败。
- 子进程通过参数列表、明确工作目录和受控环境启动；禁止将用户输入拼接进 shell 命令字符串。
- 子进程退出、超时、取消、日志收集和产物确认应有可检查的处理路径，不留下无人管理的后台任务。
- 接口变更必须说明兼容影响；不得直接破坏已约定的外部调用或已有部署模型格式。

## 7. 跨平台与私有 runtime

- 文件路径使用语言和库提供的路径接口，不手工拼接平台分隔符、盘符或用户目录。
- 明确区分安装资源、可写应用数据和临时文件，不能默认安装目录可写。
- 路径处理应考虑空格、中文和合法平台路径，禁止无条件把路径转换失败当作不可能情况。
- 平台差异集中封装，避免在界面或业务逻辑中到处散布操作系统分支。
- 运行依赖由软件管理。不得通过自动修改用户全局 Python、Conda、PATH 或驱动来掩盖兼容问题。
- 依赖版本及来源必须可追溯；版本升级应作为独立变更说明影响，不能顺带进行全量更新。
- 应用依赖的清单、锁文件和分发记录在未来建立后统一维护，不让各开发者自行选择不同版本交付。
- GPU 支持遵循软件版本对应的兼容范围，不硬编码型号白名单，不默认某台开发机成功就代表两平台均支持。
- 离线推理路径不得隐式联网调用 Agent、下载依赖或启动 Python 训练进程。

## 8. 日志、安全与数据保护

- 日志记录足够的任务上下文、阶段和失败原因，避免重复堆叠相同错误；用户提示与诊断详情分层处理。
- 禁止在日志、提交或测试夹具中泄漏 API 密钥、认证令牌、个人路径中的敏感信息或用户原始图片。
- 任务图片的在线处理授权不扩展到无关文件、凭据、其他数据集或公开上传。
- 仓库不保存用户数据集、模型权重、完整 runtime、训练缓存或生产日志；必要的小型测试资源使用可公开的合成数据并记录来源。
- 新增依赖或引入模型资源前说明用途、替代方案、分发体积和许可核查情况；不得擅自增加辅助标注模型。
- 不擅自提升权限、安装系统驱动或改变机器安全配置。
- 外部接入范围、鉴权和暴露策略尚未确定，不能默认为无鉴权公网服务。

## 9. 测试与质量要求

### 9.1 测试分层

- 新增业务逻辑应有对应测试；修复缺陷应补充能覆盖该问题的回归测试。
- 单元测试优先覆盖纯逻辑、配置校验、状态转换和结果映射，不默认依赖 GPU、摄像头、互联网或真实模型服务。
- 集成测试覆盖 Agent/训练进程接口、模型导出与 Rust 推理、OpenCV 和 ZeroMQ 接入；依赖环境必须明确标注。
- 图像和分割结果测试应关注坐标、类别、区域表达以及导出前后一致性；精度容差依据已确认规则设置，不虚构通用阈值。
- 训练相关记录应能说明使用的数据与配置，不能把 Agent 的文字判断当作已经完成的指标验证。
- 性能结论必须附带环境、输入和测量方式；没有测量不得承诺帧率或延迟。
- GPU 或平台条件不足时，明确报告对应检查未执行，不把单元测试通过写成端到端验证通过。

### 9.2 Rust 工程的基础检查

以下命令从 Cargo 工程根目录执行。当前只覆盖骨架，不能据此宣称 GPU、界面或模型功能已经验证；Clippy 需要所用工具链已有对应组件，本次实际检查方式见 README。

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

Cargo 输出目录通过仓库内 `.cargo/config.toml` 统一配置为 `depoly/target/`。Rust 集成测试放在 `depoly/tests/`，通过 `Cargo.toml` 的 `[[test]]` 显式注册；新增测试目标必须同步声明，不能只放入文件后假定会自动运行。

检查范围按实际平台与启用的后端确定，不机械添加 `--all-features`。需要 GPU 或原生库的目标应在对应环境验证，缩小检查范围时必须说明哪些部分未覆盖。

对 lint 的抑制应局部、必要且附理由，禁止为通过检查而全局屏蔽警告。Python、Slint 和跨平台打包的检查命令，在相关工程配置确定后补充；不把这些命令写成现有 CI 已执行的事实。

### 9.3 文档检查

- 检查本地链接、文件名大小写、UTF-8 编码、末尾换行和尾随空白。
- 检查 README、AGENTS.md、PRD 和本规范是否一致。
- 已确认需求、候选建议、未来规范和未决事项必须区分清楚。
- 不提交虚构的命令结果、性能数据、安装说明或实现状态。

## 10. Git 提交与代码评审

### 10.1 提交约定

- 一个提交聚焦一个可解释的目标，避免混合无关重构、格式化和功能修改。
- 提交标题采用 `type(scope): 简要说明`；无必要时可以省略 scope。
- type 使用 `feat`、`fix`、`docs`、`refactor`、`test`、`build`、`ci`、`perf` 或 `chore`，说明默认中文。
- 破坏兼容性的变更必须先获确认，并在说明中列出影响和迁移要求。
- 不提交临时调试内容、真实凭据、用户数据、模型或二进制环境。
- 自动化 Agent 仅在用户要求时创建提交或推送，不擅自重写历史、恢复已删除文件或覆盖他人工作树。

### 10.2 评审清单

评审应说明并检查：

1. 变更目的、需求依据及明确不做的内容。
2. 模块边界与方案 A 是否保持一致。
3. 错误、取消、无效输入和资源释放是否得到处理。
4. Windows/Linux、私有 runtime 和已约定接口的兼容影响。
5. 测试执行结果、未执行项目和剩余风险。
6. 安全、数据、依赖和分发影响。
7. 文档是否同步，是否误将未决产品要求变成默认行为。

当前未建立 PR 模板、CI 或分支保护规则。本节是团队协作约定，不表示这些设施已经配置完成。

## 11. 规范变更

- 规范变更需说明理由、影响范围和已有代码的兼容处理，不追求无关的全仓库改写。
- 技术问题依赖实际库版本时，核查对应版本的官方资料；不能把上游文档或示例直接当作本项目验证结果。
- 未来代码结构和工具链确定后，可补充具体命令与目录约定；不得为补齐文档而自行创建未获授权的工程。
- 规范与产品需求发生冲突时，先请求澄清，不以编码偏好推翻已确认的产品方向。
