# VisionHyperAgent 代码规范

## 适用范围与规范依据

本规范覆盖本项目手写的 Rust 后端、TypeScript/Svelte 前端和 Python ML Worker，也覆盖 `docs/models/` 中的调用 Demo。第三方源码、锁文件、纯 JSON、构建产物和机器生成文件不改写以插入注释。

| 语言 | 适用模块或文件 | 规范来源及地址 | 实际查阅日期 | 采用内容与项目差异 |
| --- | --- | --- | --- | --- |
| Rust | `source/backend/` | Rust Style Guide：<https://doc.rust-lang.org/style-guide/>；Clippy：<https://doc.rust-lang.org/clippy/> | 2026-09-22 | 采用 rustfmt、可读性、所有权和 Clippy 建议；项目额外要求功能注释密度 |
| TypeScript / Svelte | `source/frontend/src/`、前端测试和 API Demo | Google TypeScript Style Guide：<https://google.github.io/styleguide/tsguide.html> | 2026-09-22 | 采用命名、模块、类型、Promise 和导入规则；Svelte 单文件组件按项目目录职责组织 |
| Python | `source/backend/ml-worker/` 及 Python Demo | Google Python Style Guide：<https://google.github.io/styleguide/pyguide.html> | 2026-09-22 | 采用命名、导入、异常、文档字符串和测试规则；Worker 额外遵守 NDJSON 与任务目录边界 |

Google 官方 Style Guide 页面强调可读性、一致性和避免危险构造；Rust 没有对应的 Google 语言规范，因此使用 Rust 官方风格指南和 Clippy 文档。项目要求优先于参考规范中的可选风格建议。

## 命名、格式与导入

| 项目 | Rust | TypeScript / Svelte | Python |
| --- | --- | --- | --- |
| 文件与目录 | 模块文件使用 `snake_case.rs`；目录按架构模块命名 | 文件使用 `camelCase.ts` 或 `PascalCase.svelte`，组件名与文件名一致 | 模块使用 `snake_case.py`；测试使用 `test_*.py` |
| 类型 | `PascalCase`；枚举取值语义明确 | 类型、接口、组件使用 `PascalCase` | 类使用 `PascalCase`，类型别名按项目一致性命名 |
| 函数与变量 | `snake_case`；布尔值使用 `is_`、`has_`、`can_` 前缀 | 函数和变量使用 `camelCase`；事件处理函数用动词开头 | 函数和变量使用 `snake_case`；布尔值使用 `is_`、`has_` |
| 常量 | `SCREAMING_SNAKE_CASE` | `SCREAMING_SNAKE_CASE` | `SCREAMING_SNAKE_CASE` |
| 导入 | 由 rustfmt 保持格式；显式导入，避免无用 `use` | 外部包、项目绝对路径、相对路径分组；禁止循环依赖 | 标准库、第三方、项目模块分组；禁止通配符导入 |
| 格式化 | `cargo fmt` | Prettier 或项目已有 Svelte 格式化配置 | Black/Ruff 配置按实际工程启用；未配置时不宣称已格式化 |

公共名称应表达职责，不用 `Manager2`、`temp`、`data` 等无语义名称。跨模块 ID、状态、错误码和事件名必须与 API 文档保持一致。

## 注释规范

### 内容要求

- 注释简短直接，只描述对应代码的功能，例如“读取配置”“校验 manifest”“释放连接”。
- 公共类型、方法、消息和错误必须说明职责、参数、返回值、失败行为和线程边界；实现变化后同步更新文档注释。
- 不写开发过程、修复历史、需求来源、个人评价、空注释或装饰线。
- 注释必须使用语言合法语法；字符串中的 `//`、`#` 或模板文本不算注释。
- 对外 API 的注释优先描述调用者需要知道的契约，不泄漏密钥、原图内容或绝对私有路径。

### 五行注释规则

- 每连续 **5 行非空手写源码**至少包含 1 行有效功能注释；最多连续 4 行没有注释。
- 空行不稀释计数；导入、声明、括号、分支和返回行都属于非空源码行。
- 独立注释和同行注释均可计入；仅有注释符号、装饰符号或重复文字不计入。
- 多行注释中只有包含功能说明的行计入；文档字符串必须真正描述对应 API 才计入。
- 纯数据、第三方源码、锁文件和机器生成文件不插入非法注释；不支持注释的数据格式保持合法。
- `docs/models/` 的 Rust、TypeScript 和 Python Demo 同样遵守本规则；生成新 Demo 时先检查注释密度。

## 模块与接口边界

- 前端页面放 `source/frontend/src/pages/`，复用组件放现有组件目录，跨页面状态放 `source/frontend/src/lib/stores/`，HTTP/WebSocket 封装放 `source/frontend/src/lib/api/`。
- Canvas 只负责几何编辑和渲染；project-service 负责版本、类别、规则和确认校验。
- Rust 网关不直接写数据库或启动 Worker；业务服务不绕过 task-runtime 管理长任务。
- Python Worker 不连接 SQLite、不访问浏览器、不读取 Codex 密钥，只读写 Rust 指定的任务目录。
- `source/backend/depends/` 为第三方依赖，禁止直接修改；需要升级时先更新技术方案和构建入口。
- 公共数据结构、事件、错误码和方法签名发生变化时，必须同步更新对应 `docs/models/` 文档和调用方。

## 错误处理与日志

| 语言 | 规则 |
| --- | --- |
| Rust | 业务失败使用稳定错误类型或 `Result`；不可恢复启动错误向上返回；避免 `unwrap` 处理用户输入；错误链保留诊断来源 |
| TypeScript | API 错误按稳定 `code` 分支；Promise 必须处理失败和取消；组件显示可理解提示，不把堆栈直接渲染给用户 |
| Python | 区分输入错误、资源错误、取消和内部错误；Worker 将错误序列化为 NDJSON，不把完整 traceback 发给前端 |

日志使用全局日志入口，包含时间、级别、模块、位置、任务 ID 或请求 ID；禁止写入 API Key、授权头、Cookie、用户完整消息、原图内容和未脱敏外部响应。用户可见提示应说明影响和下一步，内部日志保留诊断上下文。

## 并发、异步与资源管理

- Rust Tokio 任务必须有取消、超时、退出和错误传播路径；锁只保护状态，不在锁内执行网络、文件或模型调用。
- 前端 WebSocket 事件按序归并；组件销毁时取消订阅和请求；网页关闭不取消后端任务。
- Python Worker 单任务单进程；训练、评估和推理在安全检查点检查取消；退出前刷新完成凭证、指标和日志。
- 文件写入采用临时文件加原子重命名；路径必须经过根目录校验，拒绝 `..` 穿越和符号链接逃逸。
- 进程由 desktop-host 或 task-runtime 创建并回收；不启动未经确认的 shell 命令，不遗留子进程。

## 单元测试、集成测试与代码审查

- 单元测试覆盖正常输入、边界、错误码、状态转移、取消和资源清理。
- 集成测试使用真实模块边界，验证 HTTP/WebSocket、SQLite 事务、Worker NDJSON、Codex 连接和跨平台退出。
- 前端测试验证可观察行为：状态、渲染、断线恢复、发送失败、附件和计划确认，不以快照数量代替行为测试。
- Python 测试覆盖无 GPU、显存不足、manifest 错误、Worker 崩溃、取消和完成凭证校验。
- 修 Bug 先添加可复现测试，再修复并保留回归用例。
- 审查必须检查 API 文档同步、错误分支、敏感信息、线程边界、资源释放、目录归属和五行注释密度。
